# Serious Tavern

A single-user chat app where each conversation runs a visual, reusable workflow. TypeScript/ESM throughout; no account system in this MVP.

See [Plan & Vision](PLAN.md) for the product vision and planned next steps.

## Run

Requires Node.js 24 and npm. Run `npm install`, then `npm run dev`. Open the Vite URL shown in the terminal (normally http://127.0.0.1:5173). The API runs on http://127.0.0.1:3001; Vite proxies `/api`. Run `npm run check` before committing and `npm run build` to verify the production bundle.

Create a chat and choose a workflow. The seeded **Default Assistant** uses the Default preset and requires an `openrouter` secret in Settings. **Parallel demo** makes two HTTP calls to httpbin.org and needs network access. To try a local echo without keys, make a workflow with Chat Input `message` → Chat Output `value`.

## Tooling

Run these commands from the repository root; the configuration covers all npm workspaces:

| Command | Purpose |
| --- | --- |
| `npm run check` | The single pre-commit command for agents and contributors: Biome formatting/lint checks (no writes), then TypeScript checks, all Vitest tests, and Knip. Stops at the first failing step. |
| `npm run lint` | Check lint rules only, without writing files. |
| `npm run format` | Apply Biome formatting. |
| `npm run fix` | Apply formatting and Biome's safe lint fixes. Does not enable unsafe fixes. |
| `npm run knip` | Find unused source files, exports, types, and dependencies across workspaces. |
| `npm run build` | Typecheck and build the production web bundle. |

Biome uses the recommended lint preset, two-space indentation, single-quoted JavaScript/TypeScript strings, semicolons, and a 120-column target. Import organizing and other assists are **disabled** to avoid noisy import-order changes. Generated output, `node_modules`, data directories, coverage, Playwright reports/results, TypeScript build metadata, and the lockfile are excluded. `AGENTS.md` and `PLAN.md` are owned by the orchestrator and excluded from automated changes.

Rule tuning intentionally keeps this tooling adoption behavior-preserving:

- `noNonNullAssertion` and `noExplicitAny` are off: existing validated graph lookups and flexible node/provider boundaries should not be rewritten just to satisfy stylistic checks.
- `useExhaustiveDependencies` is off: changing existing effect dependencies or callback identities can change fetching and editor state behavior; that needs a separate React-focused change.
- `noArrayIndexKey` is off: changing keys in existing ordered lists could alter component identity and state.
- `useButtonType`, `useAltText`, `noStaticElementInteractions`, `noLabelWithoutControl`, and `useAriaPropsSupportedByRole` are off: retrofitting form defaults, image descriptions, labels, and keyboard/ARIA interactions belongs in a dedicated accessibility pass, not mechanical lint adoption. Other recommended accessibility rules remain enabled.
- `noDescendingSpecificity` is off: the existing stylesheet deliberately layers page/component overrides; reordering selectors could change rendering.
- `noUnsafeOptionalChaining` is off **only in `apps/web/src/api.test.ts`**: those assertions inspect mock calls immediately after awaiting the corresponding requests. The rule remains enabled for application code.

Two existing `useOptionalChain` warnings are retained rather than applying fixes Biome classifies as unsafe.

Knip explicitly lists server startup, the web entry and Vite config, package entry points (including the shared `./ports` subpath), and test files. Its project patterns are scoped to source/config files, so live data and generated outputs are not scanned. Package entry exports are intentional workspace APIs, and tests/configs are independent roots, not dead application files. No dependency or symbol ignore list is needed. Knip may print harmless redundancy hints because its plugins also infer the explicit entry points; these do not fail `check`.

The initial Knip cleanup removed only the unused internal server `pngSignature` alias and three unused alert-barrel type re-exports (`Alert`, `AlertOptions`, `AlertLevel`); their underlying type definitions remain. No unused files or dependencies were found.

The mechanical formatting commit is listed in `.git-blame-ignore-revs`. To hide that churn in local blame:

```powershell
git config blame.ignoreRevsFile .git-blame-ignore-revs
```

## Architecture

- `packages/shared`: entity models plus the endpoint contract in `src/api/` (body, params, query, response schemas and inferred `ApiBody`, `ApiParams`, `ApiQuery`, `ApiResponse` types). The contract covers sessions/messages/executions, workflows/validation, presets/preview, characters/personas/import/export/avatars, node types/dynamic ports, providers, collections, state definitions and a chat's computed story state, secrets and the common error envelope. `src/state/` holds the story state model: definitions, the turn entries stored on sessions, the fold that turns them into values, and the snapshot a run starts from (see Story state). Binary upload/download schemas describe bytes, not JSON; card extension values and error details intentionally remain `unknown`.
- `packages/engine`: validated DAG executor, event callback, template helper, preset renderer, LLM adapter registry (`providers/`, keyed by provider `kind`), node registry, and individual node implementations in `src/nodes/<type>/index.ts`. Internal `text.ts` centralizes compact node/template serialization and pretty JSON/transcript coercion shared by execution and presets; their distinct formatting remains intentional. Nodes backward-reachable from **any sink** execute (the union of their dependencies); other nodes are logged as skipped (`not needed by any output`). A sink is a definition with `sink: true`: Chat Output and State Write today. A sink with no path to a Chat Output still runs, but a workflow still needs at least one Chat Output and only Chat Outputs produce replies. Independent ready nodes execute concurrently; condition branches skip and merges ignore skipped inputs. `executeWorkflow`'s `settings` option (chat settings resolved by the caller) reaches nodes as the read-only `ctx.settings` and templates as `{{settings.*}}`. Its `state` option (the story state snapshot) reaches nodes as the read-only `ctx.state` and templates as `{{state.*}}` and `{{trigger.turn}}`; nodes store state with `ctx.writeState(...)`, which only buffers (`StateWriteBuffer`, wired into the executor by `StateRun` in `state-writes.ts`), and the run returns the resolved `writes` (also on `ExecutionFailure`). See Story state. A sink that depends on an **After Reply** node belongs to the **post part** and runs in a second run after the turn settles (`executeWorkflow({ part: 'post' })`; `PreparedWorkflow.parts` holds the partition, computed once); every other sink, Chat Output included, is the reply part. See After Reply and post-turn runs.
- `packages/node-ui`: JSON-Schema-driven config form and optional custom panels.
- `apps/server`: `app.ts` assembles Fastify parsers, errors and resource routes; `context.ts` wires repositories, secrets and seed initialization. `routes/` parses shared contract schemas and types Fastify replies with `ApiResponse`; `services/` owns locked chat execution, preset preview, character/persona imports/exports and connector imports (`services/import/`). `errors.ts` centralizes HTTP errors and missing-entity checks. `storage/` and `secrets/` retain atomic JSON writes (presets, providers, collections and state definitions use YAML via `YamlRepository`), per-session locking and encryption. `card.ts` and `uploads.ts` handle card/image transport. `services/node-resources.ts` is the one place the server builds the repositories nodes load by id (`NodeResources`). Story state is folded by `services/story-state.ts`, appended to sessions by `services/settle-turn.ts` and served by `services/session-state.ts`. The after-reply run of a settled turn is `services/post-turn.ts` and its result is committed by `services/settle-post-run.ts`. The server owns all data and secrets.
- `apps/web`: React/Vite chat, React Flow workflow editor, Presets, Providers, State definitions, Characters, Personas, Collections, and Settings. Every tab stays mounted and inactive tabs are only hidden, so each tab keeps its open item, drafts and scroll position; the lists of workflows, presets, providers, state definitions, characters, personas, collections and chats come from shared stores (see below), so every page sees the same fresh data. `api/transport.ts` owns fetch, `ApiError`, JSON headers and automatic/silent toasts. Per-resource clients in `api/` use the shared request/response types; pages call methods such as `sessionsApi.sendMessage(id, body)` rather than declaring payloads or constructing route strings. The UI does not execute workflows.

The web shell (`apps/web/src/layout/`) implements the three-column layout of `docs/FRONTEND-LAYOUT.md`: a thin top-bar skeleton, then columns L | M | R. `state.ts` is the pure layout model (`LayoutState` and `layoutReducer`, no React): `tabs` (what L and R show; R shows `chat` while a wide editor owns M), `wide` (the wide editor in M), `narrowOpen`, `compact`/`compactTab`/`compactChat` (two-column mode), `dirty` and `kinds` (each resource's editor is `wide` or `narrow`). Actions: `selectTab`, `openEditor`, `closeEditor`, `setCompact`, `toggleCompactChat`, `setDirty`, `restore` (apply a layout read from the URL). `derive.ts` turns the state into `viewSlots` (the column each view sits in, or `null` when hidden) and the header icons per column. The rules are unit-tested in `state.test.ts`. `Shell.tsx` mounts every view exactly once, in a fixed order, as a child of one CSS grid; moving the chat between M and R, or hiding it, only changes a view's `grid-area`/`hidden`, so React never remounts it (streaming turns, composer drafts, scroll, hosted pages and the React Flow canvas survive). `useChat` lives in the shell and feeds both the chat list (`ChatSidebar`, in R) and the conversation (`pages/Chat.tsx`). Columns are resized with a hand-rolled `ResizeHandle` (pointer drag and arrow keys); `widths.ts` clamps them (side minimum 180px, M minimum 360px) and remembers them in `localStorage` (`st.layout.widths`, access wrapped in try/catch). The layout collapses to L | M below a 1000px viewport (`useCompactMode`). Below 700px (phones, `useMobileMode`) it is the same two-column state shown one column at a time: `mobile` and `pane` (`'L' | 'M'`) in the state, `setMobile` (which also enters compact mode) and `showMiddle` (show M with the chat or the wide editor; a no-op outside phone mode). `viewSlots` hides whatever is not in `pane`, and `mobileView` names what is on screen. Picking a list shows L, opening a wide editor or a chat from the chat list shows M, opening a narrow editor shows L; a restored URL shows the editor it opens. On a phone the URL also carries `view=<list>|chat|editor` when what is on screen is not what the rest of the URL opens (`defaultView`), and `sameContent` counts it as content, so switching views from the menu is a `push` and Back steps through them. While the editor on screen has not loaded its item yet (`phoneEditorLoading`), `useLayoutUrl` holds the URL, so the half-open layout never becomes a history step. Desktop never writes `view`. The top bar, the L icon row and the resize handles are not rendered on a phone; the M header carries a menu button (with a dot when any editor is dirty) that opens `MobileMenu`, a native `<dialog>` drawer listing the chat, the open wide editor and every list. Editors adapt with container queries: the preset editor stacks into one column below 640px, and the workflow palette becomes a scrolling strip with the config panel covering the canvas below 560px. Header icons take a `dirty` flag (`setDirty`), shown as a dot. Workflows and presets are split into a list (`WorkflowList`, `PresetListView`, in L) and a wide editor (`Workflows`, `Presets`, in M). They share state through a per-resource editor store (`stores/editorStore.ts`: `workflowEditorStore`, `presetEditorStore`): the draft stays inside the always-mounted editor, and the store carries only the open item id, its dirty flag and the list's requests (`open(item, focus?)`, `discard(id)`, applied once each by `useEditorCommands`; `focus` is a hint inside the item, e.g. the edge to highlight). Opening another item sets the store's `currentId` to it right away, so the layout URL changes once, to the new item, instead of first recording the old one for the render before the editor applies the request. The list also calls `useLayoutActions().openEditor` (a context whose value never changes, so the prop-less list views stay constant elements) to show the editor in M; `useDirtySync` mirrors each store's dirty flag into the reducer's `setDirty` for the header dot. Selecting an already-open item never reloads it, so its draft survives. Editors adapt to M with CSS container queries (`.view[data-view^="editor:"]` is the `editor` container). Characters, personas and settings are narrow editors that open inside their own column (`DESIGN_KINDS`). Characters and personas have their list in R (`CharacterList`, `PersonaList` in `pages/Entities.tsx`, both `EntityListView` wired to an `EntityKind` from `pages/entities/entityKinds.ts`) and share the same editor-store link as the wide editors (`characterEditorStore`, `personaEditorStore`): picking an item calls `editorStore.open` and `openEditor`, which makes `viewSlots` replace the list with the editor in the same column; the editor's back arrow calls `closeEditor`, which only hides it, so its draft stays and its icon keeps the dirty dot. Opening a wide editor sends the chat to R and hides the narrow editor; closing the wide editor brings it back with its draft. Create and import (file picker or drop, on the list and on the editor) live in `entityActions.ts`; a file dropped on an editor with unsaved changes is imported but does not replace the draft. Collections work the same way in R (`CollectionListView`, `Collections` in `pages/collections/`, linked by `collectionEditorStore`; see Authored collections). Providers and state definitions are the narrow editors with a list in L (`ProviderListView`/`Providers` in `pages/providers/`, linked by `providerEditorStore`; `StateDefinitionListView`/`StateDefinitions` in `pages/stateDefinitions/`, linked by `stateDefinitionEditorStore`); they work like characters, only in L. L's header icons are workflows, presets, providers, state definitions (`Brain`) and settings. The prop-less views and the dirty sources are the module-level constants `STATIC_VIEWS` and `DIRTY_SOURCES` in `layout/staticViews.tsx`. Settings has no list (`LISTLESS` in `state.ts`): its icon shows the form directly in L and it has no `list:settings` view. In two-column mode all of these live in L. Entity styles are in `pages/entities/entities.css`: a single-column form by default, with a roomier layout from a container query when the column is dragged wide. The layout lives in the URL, so a reload restores it and a copied URL reproduces it: `/?session=<id>&left=presets&wide=preset:<id>&right=character:<id>`. `session` is the open chat, `left` is L's tab (`workflows` default, `presets`, `providers`, `stateDefinitions`, `settings`; `provider:<id>` and `stateDefinition:<id>` mean that editor is open), `wide=workflow|preset[:<id>]` is the wide editor in M, `right` is R's tab (`chats`, `characters`, `personas`, `collections`, or `chat` while a wide editor owns M; `character:<id>`/`persona:<id>`/`collection:<id>` mean that narrow editor is open), and `edge=<id>` is a one-shot highlight for the opened workflow. Defaults are omitted, so the plain layout is `/`. Column widths stay in `localStorage`; dirty flags, drafts and compact mode (derived from the viewport) never go into the URL. `layout/url.ts` holds the pure functions (`parseLayoutUrl`, `formatLayoutUrl`, `layoutToUrl`, `urlTarget`, `layoutHref`; round-trip tested, garbage falls back to defaults) and the reducer's `restore` action applies a parsed URL. `useLayoutUrl` keeps both in step. Layout to URL: a change of content (chat, editor or item) is a `push`, so Back/Forward step through what was opened, and tab switches are a `replace`. An editor that has no item open is not written to the URL. URL to layout: a URL the hook did not write (Back/Forward, a clicked link, a pasted URL) is `restore`d, its items are opened through the editor stores once their lists load, and the URL is not rewritten while that runs. Afterwards the real state is written back with `replace`, which normalizes the URL and drops what could not be opened: an id that no longer exists closes its editor (the list stays), an unknown chat is ignored, and garbage values fall back to defaults. Back/Forward never replaces an editor's unsaved draft nor switches a streaming chat; a clicked link does replace a draft, like a click in a list. A link without `session` leaves the open chat alone, while stepping Back to a URL without one closes it. Link producers build URLs with `layoutHref` (toast links, `PresetPreview`). Old paths stay as inbound aliases (`legacySearch` in `layout/routes.ts`): `/workflows?workflow=…&edge=…`, `/presets?id=…`, `/characters`, `/personas`, `/collections?id=…`, `/settings` (node-ui's "Edit preset" and "Edit collection" links use `/presets?id=…` and `/collections?id=…`) are rewritten with `replace` to the layout URL, and unknown paths become `/`.

Shared lists live in `apps/web/src/stores/`. `createListStore` (`listStore.ts`) holds one server list outside React, in the style of the alert store: it loads when the first subscriber appears, re-fetches when its change event arrives on the shared `EventSource` (which the server also sends on every connect), sorts with the list's comparator (`compareRecent` for workflows, presets and chats, by name for characters, personas and collections) and keeps the array identity when nothing changed. `stores/index.ts` instantiates one store per resource and exposes `useList(store)` (a `useSyncExternalStore` wrapper). `store.refresh()` fetches now and resolves with the list; calls in the same tick, or during a fetch, share one fetch, so event bursts and a page's own post-save refresh collapse into few requests. Stores only feed list views and selectors: open drafts (workflow, preset, provider, state definition, character, persona, collection editors) and the open chat session are separate state and are never replaced by a list refresh. Settings data (secrets, import sources) has no change events and is still fetched by its page.

Frontend notifications live in `apps/web/src/alerts/`. Import `alerts` and call `alerts.error(message)`, `.success`, `.info`, or `.warning` from any module; React components can use `useAlerts()`. API failures toast automatically unless a request uses `{ silent: true }` to handle an error inline.

`pages/workflows/` contains controlled canvas/editor hooks, the node view, palette, toolbar, configuration panel and tested canvas conversion model (including read-only unknown-node placeholders). The toolbar's **Chat settings** toggle (with a count of declaration problems) opens `WorkflowSettingsPanel` in the config panel's place (a selected node's config wins while it is selected; clicking the toggle then deselects the node and shows the settings again; on a phone the toggle shows only its icon): one `SettingRow` per declaration with key, type, label, a default control matching the type, `min`/`max`/`step` for numbers (blank = unset), options one per line for enums, "Several lines" for text, a description, and move up/down/remove buttons. The declarations are part of the workflow draft (dirty flag, saved with the workflow; an older workflow without them is normalized to `[]` on open, so it doesn't look changed; stored items are kept raw, and one that doesn't parse is a read-only row) and problems from `workflowSettingIssues` show next to the field they concern while typing. The pure draft helpers are `settingsDraft.ts`. Node config panels receive the draft's readable declarations as `NodePanelContext.settings` (`macroHints` keeps the usable keys once each), so template fields hint `{{settings.<key>}}`; the preset editor hints every key any workflow declares (`settingsCatalog`). Duplicating a workflow copies its declarations. `pages/presets/` retains its existing list/editor/entry/preview components.

`pages/entities/` shares the list view, detail/avatar/drop components and draft/CRUD/import logic between characters and personas; an `EntityKind` supplies the per-type API calls, stores, validation and notifications, with separate field editors.

`Chat.tsx` is a thin composition of focused components in `pages/chat/`: `ChatSidebar`, `ChatHeader` (including shared character/persona selectors and the chat panel toggle), `ChatPanel` (see Chat settings; its Story state section lives in `pages/chat/story/`, see Story state in the web), `MessageList`, `ChatMessageView`, `MessageContent`, `MessageActions`, `MessageEditor`, `Composer`, and `ExecutionDetails`. `useChat` owns session/loading/send state; `useMessageActions` owns persisted edits/deletions. `useStickToBottom` tracks proximity to the bottom and observes content resizing (including images and execution details). Chat-only styles live in `pages/chat/chat.css`; the reusable accessible `IconButton` and its styles live in `components/`.

### Chat controls and rendering

- The composer grows up to 200px before scrolling. **Enter** sends, **Shift+Enter** adds a newline, and IME composition never submits. Sending retains/restores composer focus. While sending or mutating a message, the composer is read-only and sends/actions/context changes/chat navigation are disabled; workflow execution shows animated pending dots (respecting reduced-motion preferences).
- Both user and assistant bubbles render Markdown, including GFM tables, lists, blockquotes, inline code and fenced code. Links open in a new tab with `rel="noopener noreferrer"`. Raw HTML is skipped and unsafe link protocols are rejected by the Markdown renderer; no `rehype-raw` is enabled. Soft line breaks are kept visible with scoped `white-space: pre-line` on Markdown paragraphs/list items rather than another plugin dependency; code uses its own whitespace rules.
- User bubbles use the selected session persona's name/avatar, falling back to “You” and a user icon. Assistant bubbles preserve each reply's speaker snapshot and character avatar, or show “Assistant” with a bot icon. Consecutive outputs remain separate bubbles with their own identities.
- Opening a conversation scrolls to its bottom. New messages and content resizes stick only when the reader was within 96px of the bottom; scrolling back through history opts out until the reader returns near the bottom.
- Hover or keyboard-focus a bubble to expose **Edit/Delete** icon buttons (always visible on touch devices). Editing is inline: **Ctrl/Cmd+Enter** saves, **Escape** cancels, and whitespace-only content cannot be saved. Deletion requires a small inline confirmation; deleting the last surviving reply of a turn that stored story state, when that would change a value, asks with a dialog that lists what it undoes instead (see Story state in the web). Both actions work on either role and never re-run a workflow or alter message attribution/execution metadata. Changes affect history used by subsequent turns, not saved execution logs.
- A reply whose turn stored story state shows a small **Database** button, "What this turn stored" (see Story state in the web): the last reply of the turn only when it has several, and nothing for a turn that stored nothing, whose replies were deleted, or while the reply is still streaming. It opens an inline card under the button (not a floating popover: the thread scrolls, and an inline card works unchanged on a phone) that lists the writes in plain words; Escape or a second click closes it, and opening it scrolls the card into view.

### Streaming

Sending a message posts to `POST /api/sessions/:id/messages/stream`, which answers with server-sent events (`turn.start`, `node.delta`, `turn.complete`, `turn.error`; see `turnEventSchema`). The web client reads them in `api/turnStream.ts` and `useChat` applies them with the pure helpers in `pages/chat/turnMessages.ts`:
- The composer shows the user row immediately and appends one assistant row per streaming Chat Output as `node.delta` events arrive. The "Preparing a reply" indicator only shows until the first row exists.
- A collapsible **Reasoning** block appears above a message when the model emits reasoning content; it is open while no answer text has arrived yet.
- `turn.complete` replaces the local rows with the persisted messages and execution.
- **Stop** (button, or Escape in the composer) only calls `POST /api/sessions/:id/stop` and keeps reading the stream. The server cancels the LLM call and ends the stream with `turn.error` `TURN_STOPPED`, whose `details` (`turnFailureDetailsSchema`) carry the saved user message and the replies so far as `partial` rows (shown with a "Stopped" note). The same details come with `WORKFLOW_EXECUTION_FAILED`, so a failed turn keeps its partial replies without a refetch. Aborting the connection is only a fallback when the stop request fails, and a dropped connection resyncs the session from the server.
- While a turn runs the chat is locked: no switching, creating or deleting chats, and no message edits. The lock ends with the stream: an after-reply run (see After Reply and post-turn runs) that follows the reply does not lock the chat, and a message sent meanwhile is queued by the server.
- Streaming can be disabled per LLM node in its config (default enabled); the reply then arrives in one piece.

Web-only dependencies: **`lucide-react`** supplies tree-shakable SVG icons without runtime CSS; **`react-markdown`** renders Markdown safely as React elements; **`remark-gfm`** adds tables, strikethrough, task lists and autolinks. No HTML-processing or syntax-highlighting plugin is added.

The scrollable history region intentionally has `tabIndex={0}` for keyboard scrolling (a narrowly documented Biome suppression); icon-only buttons have accessible labels and titles.

To add a node type: (1) create `packages/engine/src/nodes/<type>/index.ts` exporting a `NodeDefinition` with Zod config, typed ports (`dataType`, optional `description`), defaults and `execute(ctx)`; (2) optionally add `resolvePorts(config, resources)` for instance-specific ports (resources provide read-only access to presets and character cards without importing server code), and declare `templateFields` for config fields accepting `{{...}}`; (3) register the definition in `packages/engine/src/registry.ts`; a node that needs randomness calls `ctx.random()` (next value in [0, 1) of a deterministic stream for that node and run), never `Math.random`; (4) optionally add a custom config panel. Set `sink: true` on a node that must run even when no Chat Output depends on it (it writes somewhere); it and its upstream then always run. The registry derives the required descriptor flag `dynamicPorts: boolean` from the presence of `resolvePorts`, and sends `sink: boolean` on every descriptor; no editor node-type allowlist is needed. `/api/node-types/:type/ports` resolves both input and output ports for every advertised dynamic node on canvas load, config changes and resource refreshes.

Dynamic port updates preserve controlled canvas state, refresh React Flow's handle geometry and ignore stale responses, including after reloading a canvas with identical node ids/configs. Resolution failures show an error and restore the node type's static ports. Unknown-node placeholders are never resolved. Edges attached to disappearing ports are **pruned** (dropped) once the node's ports resolve without them; the same rule runs in the engine (`pruneInvalidEdges`) when a preset is updated and when a workflow is saved. Pruning only trusts successfully resolved ports, so unknown types and failing resolvers keep their edges.

WORKFLOW_INVALID errors carry structured issues: `prepareWorkflow`/`validateWorkflow` return `ValidationIssue`s (`{ message, edgeId?, nodeIds? }`) whose messages name nodes as `Label #k (type)` (`nodeDisplayName`) instead of ids. The web transport renders those messages in the toast and links it (`layoutHref`) to `/?wide=workflow:<id>&edge=<id>`, where the editor opens the workflow and highlights the offending connection in red.

Register custom panels in `packages/node-ui/src/index.tsx`'s `customPanels` map; focused panels live in `src/panels/`. `NodeConfigPanelProps` contains `{ descriptor, config, onChange, context? }`. The optional `NodePanelContext` contains `{ presets: readonly Preset[], characters: readonly Character[], providers: readonly Pick<ProviderView, 'id' | 'name'>[], loadModels?(providerId, { refresh? }): Promise<ProviderModelList>, renderLink?(to: string, label: string): ReactNode, settings?: readonly Pick<WorkflowSetting, 'key' | 'type' | 'description'>[], stateDefinitions?: readonly StateDefinition[] }` (`settings`: the open workflow's chat settings, hinted in template fields; `stateDefinitions`: the whole definition records, for the State Read and State Write panels and the `{{state.*}}` hints). The web editor passes fetched resources and a React Router link renderer; node-ui never imports web API clients or router code. LLM and Character panels use the same context, defaulting to empty lists when absent. The LLM panel's Model field is the `ModelPicker` (`panels/ModelPicker.tsx`): a combobox (ARIA roles, arrow keys, Enter, Escape) over the list `loadModels` returns, with a lucide refresh button that passes `refresh: true`. The input is the config value, saved on every keystroke, so any id works and `config.model` stays a plain string; the list only suggests. Options are filtered by id and name (every whitespace-separated term must match, capped at 50 shown) and show the name, id, context size and price per 1M tokens when known; the pure logic is in `panels/modelOptions.ts` and the loading state machine in `panels/useModelList.ts` (reloads when the provider changes, ignores replies for a previous provider, never throws: an error becomes an inline message). A model typed that is absent from a loaded list gets a quiet hint. Without `loadModels` the field is plain text. The web editor passes a loader built on `providersApi.models(id, refresh, { silent: true })` (module-level in `WorkflowConfigPanel.tsx`, so the panel's effect stays stable); its styles are in `pages/workflows/modelPicker.css`. Without a link renderer, the LLM's preset link uses a normal anchor. Generic panels retain macro-registry-driven template hints. The **Recall** and **Draw** panels (`panels/recall.tsx`, `panels/draw.tsx`) take `NodePanelContext.collections` (`Pick<CollectionSummary, 'id' | 'name'>[]`, the web editor passes `collectionsStore`): `CollectionPicker` lists the picked collections in config order (an id with no record shows as `Unknown collection (<id>)`, with the full text as a tooltip and no Edit link; a repeated id shows once), each with remove, move up/down for Recall (its order is the output order) and an "Edit ↗" link to `/collections?id=<id>`, plus a select to add a collection not yet picked. Tag lists are comma-separated text and numbers are text fields, both through `DraftInput` (`panels/DraftInput.tsx`): it keeps what is typed (a trailing comma, a cleared number), commits only valid values, follows outside changes and reverts an invalid text on blur. Recall's separator is shown escaped (`\n` for a new line, `collectionConfig.ts`). Draw's level selects offer Any (the key is removed) and 1–5. Defaults shown come from the descriptor's `defaultConfig`. In the web editor `renderLink` is `PanelLink` (`pages/workflows/PanelLink.tsx`): a collection link opens the collection editor in R, and a state definition link (the `/state-definitions?id=` alias, "Edit definition ↗") opens the definitions editor in L, next to the open workflow, like a click in their lists, instead of following the URL, which would close the workflow (`panelLinkTarget` in `layout/routes.ts` decides; modified clicks (new tab) and other links route through their URL). Picker styles are in `pages/workflows/workflows.css`.

The generic array editor supports only arrays whose item schema is an object with exactly two required string properties, `key` and `value` (e.g. HTTP headers). Other array shapes, tuple schemas and malformed stored row values are shown as read-only JSON with an unsupported notice; they are never coerced into key/value rows or changed implicitly. Add a custom panel for those fields, as the LLM panel does for its string-array stop sequences. The generic form shows a field's zod `.describe()` text as a hint under it. A number field without a schema default is stored as unset when cleared, so the node applies its own fallback (Random's blank `min`/`max` mean per-mode bounds); a field with a default stores 0 when cleared, so the default never reappears while the user is typing.

`prepareWorkflow(workflow, resources?)` returns `{ errors, prepared? }`. On success, `PreparedWorkflow` holds a cloned workflow with parsed/defaulted configs, node definitions, resolved ports, incoming/upstream dependencies, sink reachability (nodes some sink depends on) and execution-scoped cached resources. Every node is validated, including disconnected nodes; each dynamic port resolver runs once. Resource lookups cache promises (including missing resources) and clone fetched cards/presets, so preparation and execution share the same snapshot. Resource-specific loading belongs in node port resolvers, not the executor.

`validateWorkflow(workflow, resources?)` is a thin wrapper returning preparation errors. `executeWorkflow(workflowOrPrepared, options)` prepares raw workflows internally; callers that need validation before side effects should prepare once and pass the result. Prepared workflows are execution-scoped: prepare anew for each turn, rather than reusing a snapshot across turns. The chat service prepares before saving the user message, so invalid workflows commit neither messages nor execution logs.

### Chat Output and Character nodes

A valid workflow has **exactly one Chat Input and one or more Chat Outputs**. Each successfully completed Chat Output appends one assistant message. An output skipped by a Condition branch appends nothing; a run where all outputs are skipped succeeds with no assistant messages and an execution warning.

**Chat Output** takes required `value` (`text`) and optional `character` (`character`) inputs. Its config has `template` (default `''` uses `value`; a nonempty template is rendered), `name` (optional free text, default `''`) and `order` (number, default `0`). Speaker precedence is the connected character's name, then the configured name, then an unnamed assistant. Merely selecting a session character does not automatically name outputs. Its `reply` (`text`) output remains connectable: `foo.reply → bar's LLM preset input → bar.value` chains two speakers inside one workflow run.

Produced messages are ordered by dependency first. Output Y comes before output X when Y's transitive upstream node set is a strict subset of X's; this covers both "Y feeds X" and outputs fed by a shared upstream node (e.g. `LLM1 → Output1` and `LLM1 → LLM2 → Output2` always give Output1, then Output2). Among outputs with no remaining predecessor, smaller `order` wins, then node id (stable lexical comparison). `order` therefore only breaks ties between outputs that don't depend on each other; it never puts a dependent output before its dependency, and outputs with identical upstream sets are independent. Streamed rows use the same ranking, so they never jump when the turn settles. Node finish times and canvas positions never decide message order. `order` controls message placement, not node scheduling.

**Character** emits a character card on its `character` output. Choose “Session character” (`source: 'session'`, the default) or a specific card (`source: 'card'`, `characterId`). A missing session character fails with an actionable error. Missing selected cards are validation errors. Connect a Character to Chat Output for speaker attribution, to LLM for local prompt context, or both.

The **LLM** has an optional `character` input in addition to preset inputs. A connected card replaces the session character only for that LLM's render context, including recursive `{{character.*}}` fields and aliases (`{{char}}`, `{{description}}`, `{{personality}}`, `{{scenario}}`). Without a connection, session behavior is unchanged. The preset input key `character` is reserved for this dedicated port; conflicting presets fail port resolution with an explicit error.

**Chat Settings** (category Chat) has no inputs. Its `settings` output (`object`) holds every chat setting the workflow declares, resolved for this chat (see Chat settings); its `value` output (`any`, optional) is the one named by the `key` config. With an empty `key`, or one the workflow doesn't declare, `value` is absent, so what it feeds is skipped (an undeclared key also logs a line in the node's `logs`). Templates read the same values as `{{settings.<key>}}` without the node.

### After Reply and post-turn runs

Work that must not delay or endanger the reply (extraction, memory notes, summaries of older history) runs as a **second run after the turn settles**. **After Reply** (category Chat) has no inputs and marks that work: its `replies` (`messages`), `text` (`text`, the replies' contents joined by a blank line) and `turn` (`number`, the turn's number: 1 for the first reply) outputs only have values in the after-reply run (in the reply run the node is skipped, as `runs after the reply`). More than one After Reply node is allowed.

**Partition.** `partitionWorkflow` (`packages/engine/src/parts.ts`, called by `prepareWorkflow`) splits the sinks: a sink with an After Reply node among its transitive upstream nodes is a **post-turn sink**, every other sink is a **reply sink**. Each part holds its sinks and everything they depend on. A workflow without post-turn sinks has no after-reply run at all, and nothing else about it changes. A Chat Output cannot be a post-turn sink (its reply would be written before the run that feeds it): that is a validation issue, `"Chat Output #1 (chat-output)" can't depend on "After Reply #1 (after-reply)": replies are written before it runs.`, with `nodeIds` and the offending connection as `edgeId`, so the editor highlights it.

**A node needed by both parts runs again in the post part.** Chat Input always does; so does anything a reply sink and a post-turn sink share, such as an LLM wired to a Chat Output and to a post-turn node (two provider calls, possibly different answers) or a State Write whose `value` output feeds after-reply work. Nothing is memoized. Feed after-reply work from After Reply's outputs, not from the reply's own nodes. **State writes are never repeated**: in the post part only the nodes that are exclusive to it (not in the reply part) contribute state writes, definition writes and implicit node writes such as Draw's `draws` alike. A node both parts run has its requested writes dropped when it completes there, and the post log says so in a warning (`"State Write #1 (state-write)" also ran in the reply run, so its state writes were not repeated in this run.`; only when it had asked for a write). So a reply-part `increment` wired into an After Reply consumer counts once per turn, and a post-only State Write still writes.

**What the post part gets.** The same Chat Input as the reply part (the history before the turn's user message, `trigger.message` = the turn's content, `''` for an empty send), the same resolved chat settings, character and persona. The seed is derived (`postRunSeed(turnSeed)` = `${turnSeed}:post`, pinned by a test), so its rolls differ from the reply run's but a log's seed still reproduces them; the log's `seed` is the one that seeded its nodes. The state snapshot is folded after the reply part's writes were committed and **read at the turn that just finished** (`foldStoryState`'s `turn` option): `ctx.state.turn`, `{{trigger.turn}}` and After Reply's `turn` are all that turn's number, a key the reply wrote reads `turnsSinceWrite: 0`, and Draw's `avoidRecent` window counts this turn's draws as recent. Writes are buffered and resolved exactly like a turn's (ids `<postExecutionId>:<nodeId>:<n>`, increments computed from that snapshot, completed nodes' writes kept when the run fails or is stopped). The post log lists only the post part's nodes; the reply log lists post-only nodes as `skipped` with a log line saying they run in the after-reply run (so its execution details don't read as if that work never ran). The "No Chat Output nodes ran" warning is for the reply part only, and the post part never records replies.

**Server flow** (`services/chat.ts`, `services/post-turn.ts`). After the turn settles (replies and the turn's entry saved, `sessions.changed` published) the reply is complete: the response, or the SSE stream's `turn.complete`, is delivered and the stream is **not** held open. The post run then runs as a follow-up inside the turn's own queue slot (`RunningTurn.after`, `TurnRegistry`), so the next message to the chat waits for it, even one that was already queued when the reply settled, and **Stop** (`POST /api/sessions/:id/stop`) stops whichever job runs: here the post run, which ends `stopped` (the user stop reason applies). A message queued behind a post run starts when it ends; its stream has no headers until then (a known limitation: there is no `turn.queued` frame). Stop (`POST .../stop`) while it waits stops the post run, not the queued message; to cancel the queued message the web client aborts its request instead. The routes watch the client's connection from the moment the request arrives, so a message whose client leaves while it waits (a reload, a closed tab, an aborted request) is cancelled when it reaches the front of the queue and stores nothing; the plain `POST .../messages` only cancels a message that has not started (once it runs it finishes). Other chats are never delayed. Deleting a chat stops its running post run. A post run only follows a turn that **ran to the end**: a failed or stopped reply leaves none. A completed turn with no reply (every Chat Output skipped) does run it, with `replies: []` and `text: ''`. The post run has its own execution log (`part: 'post'`, `turnExecutionId` linking the reply run's log, `seed` as above) fetched like any execution (`GET /api/executions/:id`). Its failure, or a log that cannot be written, never touches the reply or the turn's messages; it is recorded on the turn's entry (see Story state). If the chat was deleted meanwhile the run ends with no settle, no file and no event. The write that records the result is retried once; if it still fails a minimal write records an `error` saying the result could not be saved (the run's writes are lost with it), so the entry is never left `running` to read as a restart's casualty. `app.close()` stops running post runs (`shutdown` stop reason) and waits for them (`TurnRegistry.close()` in an `onClose` hook), so nothing writes after the data directory is gone; a run stopped that way is recorded as the same interrupted `error` a crash shows (its completed nodes' writes are kept), not as a user's `stopped`. The post part uses the state definitions listing of the turn start, so its ports and its snapshot cannot disagree with the reply part's.

### Message links and summaries

Any collection item can **link to chat messages**; summaries are one use of that (so are facts taken from a message, a mood per reply, an open thread and where it started). There is no summary store, node or session field: what makes a key "summaries" is only how it is wired. Design and reasoning: `docs/explorations/STATE-DESIGN-AMENDMENT-1.md`.

**The link.** An item may carry the built-in `messages: { ids, fingerprint }` next to `id` and `text`: the ids of the messages it is about, in chat order, and `fingerprintMessages` of them (a stable hash of each message's id, role, name and content, in order; it must never change). It is not a declared field, so every collection accepts it and the definition's `fields` stay text/number/boolean (a field called `messages` or `link` is refused when a definition is written). Links are set only by State Write's `messages` input: a `value` object's own `messages` key is an ignored undeclared field, so a write never links by accident. Ids only, never positions or turn counts (a turn has several replies or none, and deleting a message shifts every position after it). Linked items follow the story state lifetime rule unchanged: they live as long as the replies of the turn that wrote them.

**Status is computed on read** (`linkStatus`, shared; never stored) from the chat's history messages: `intact` (every linked message exists and the fingerprint matches), `changed` (all exist, at least one was edited), `partial` (some were deleted, the rest may be edited), `gone` (all deleted). A run's snapshot gives each linked item a read-only `link: { status, ids, first }` (`first`: the 1-based position of its first surviving linked message among the run's history messages; absent when gone), which templates and State Read see; a node that works from the chat (Next Chunk, Unlinked Messages) judges the same history, so they never disagree. Readers decide what to do with a broken link: only intact items are used.

**Replaced.** A broken item is *replaced* when intact items of the same key link every one of its surviving messages (a `gone` item is never replaced): a re-summarized chunk needs no `remove`. **Chat order.** Collections keep items newest first, which is the wrong order for linked items (a redone summary of messages 21-40 is written after the one of 41-60), so `linkedInChatOrder` gives the intact linked items by their first linked message (ties keep newest first; an item linking exactly the same messages as an earlier one is dropped, which happens when an edit is reverted after the chunk was redone). The `linked` template helper and State Read's `linked` read both use it.

**State Write `messages`.** The input exists only for `add` on a collection key and is `requiredIfConnected` (a skipped source skips the write). It takes a link (`{ ids, fingerprint? }`, e.g. Next Chunk's `link`), one message, or a non-empty list of messages (their ids in order, repeats dropped; e.g. After Reply's `replies`); anything else is a node error naming what it got. The buffered `add` carries the link, and the node's log says `linked to N messages`. The fingerprint is checked or taken when the run settles (see the server part below).

**Next Chunk** (category History) finds messages a collection key does not cover yet; nothing in it is about summaries. Config `definitionId` and `key` (a collection key; an unset, unknown or non-collection target is "not set up", like State Read, and a validation issue), `chunkSize` (whole number from 2, default 20) and `rawWindow` (default 16: the most recent messages are never planned; keep it at least as big as what feeds the prompt raw). Optional `after` input (`any`, nothing is read from it; connect After Reply so a post run starts it). Over the messages outside the raw window it plans, with the pure `planNextChunk` in shared: the first item (in chat order) that is not intact **and not replaced** is re-planned over its surviving messages that no intact item covers (`replaces` = its id; a re-plan may be shorter than `chunkSize`); else the first run of `chunkSize` consecutive messages that no intact item links; else nothing, with the reason in the node log, every output absent and everything wired after it skipped. Outputs, all optional: `messages`, `text` (Memory's transcript format), `link` (`{ ids, fingerprint }`, for State Write's `messages`) and `replaces` (text, the broken item's id, for users who want to wire a `remove`).

**Unlinked Messages** (category History, not a sink). Input `messages` (required); config `definitionId` and `key` (a collection key; an unknown or non-collection key is a node error when it runs, like Recall's unknown collection). Outputs the input minus the messages that **intact** items of the key link to, in the input's order (`messages`), and as a transcript (`text`). Broken items hide nothing, so their messages stay. Whether an item is intact is judged against the whole chat, not against the input list.

**Memory** is plain recent history again (`lastN`, `format`), plus `all` (default false): the whole history, `lastN` ignored (`lastN: 0` still means none). Use it before Unlinked Messages, since a Last N would cut messages that no summary covers yet.

**Summaries, wired.** Declare a collection key (for example definition `memory`, key `summaries`) **without a `cap`** (a cap drops the oldest summaries and their messages reach the prompt raw again). Several summary sets are several keys.

```
Reply part:
  Memory (all) -> Unlinked Messages (memory.summaries) -> LLM input "recent"
  preset entry: {{#each (linked state.memory.summaries)}}{{text}}{{/each}}
After-reply part:
  After Reply -> Next Chunk (memory.summaries, chunk 20, raw window 16) -text-> LLM (summarize) -text-> State Write (memory.summaries, add) value
                               \------------------------- link ------------------------------------> State Write messages
```

The prompt gets the intact summaries in chat order from the preset and every message no intact summary stands for from the LLM input: the raw window, the messages that do not fill a chunk yet, and the messages of broken summaries. Accepted caveat: with those as separate inputs, a broken summary in the middle puts its raw messages after later summaries until the next turn re-summarizes it. The raw window guarantees that summaries never cover the newest messages when they are written. Edits and deletes after a chunk leave its summary alone; inside a chunk they break the link, so readers ignore it and Next Chunk redoes it after the next reply; deleting or regenerating the turn that wrote a summary removes it (the regenerated turn's post run summarizes the chunk again: one extra LLM call).

### Random and Parse JSON nodes

**Random** (category Logic) draws exactly once per run from `ctx.random()` (see the run seed under Data and secrets), so the same seed gives the same result. Every mode outputs `roll`, the raw draw in [0, 1), and the node's output (with `roll`) is stored in the execution log. Its `mode` decides its ports:

| Mode | Inputs | Outputs | Result |
| --- | --- | --- | --- |
| `number` (default) | none | `value` (`number`), `roll` | Uniform number from `min` up to (not including) `max`; blank bounds mean 0 and 1. |
| `integer` | none | `value` (`number`), `roll` | Whole number from `min` to `max`, both included; blank bounds mean 1 and 6 (a die). Bounds must be whole numbers. |
| `pick` | `items` (`array`, required) | `value` (`any`, optional), `roll` | One item of the list, returned as is. An object item whose `weightField` (default `weight`; blank turns weights off) holds a number is weighted by it; any other item weighs 1, including a weight given as text. A weight that is 0, negative or not finite is never picked. When nothing can be picked (empty list, all weights 0), `value` is absent, so what it feeds is skipped. |
| `chance` | `probability` (`number`), `value` (`any`) | `value` (`boolean`, shown as Result), `true`, `false` (`any`, optional), `roll` | True when the draw is below the probability: the `probability` input when connected (clamped to 0..1; a non-number is a node error), otherwise the `probability` config (default 0.5). Like Condition, the `value` input (or the result itself when nothing is connected) goes out of the `true` or `false` output and the other branch is skipped. Both inputs are `requiredIfConnected`: when one is connected but its source was skipped (a branch not taken, a pick with nothing to pick), the whole node is skipped, as a Condition would be, instead of sending its boolean down a branch or falling back to the configured probability. |

`min > max`, non-whole integer bounds and a configured probability outside 0..1 are config errors, reported before the run (bounds are only checked in the modes that use them). Ports that a mode doesn't have are dropped from the node's connections when the mode changes; `value` exists in every mode, so its connection survives.

**Parse JSON** (category Logic) reads one JSON value out of its required `text` input, typically an LLM answer. Its `expect` config (`any` by default, `object`, `array`, `number`, `boolean` or `text`) is also the type of its `value` output. It looks for the value in this order: the trimmed text, when it is valid JSON as a whole (so a string holding a code fence stays intact); otherwise, if it contains a Markdown code fence (```` ``` ```` or ```` ```json ````), the content of the **first** fenced block only (an unterminated fence runs to the end, as in a truncated answer; when that first fence is empty, as with a reply to a prefilled ```` ```json ```` that ends in the closing fence, the text before it is used instead); then that candidate as JSON; then the first **top-level** `{…}` or `[…]` in it that parses and has the expected type, so a `[1]` reference or a `[0, 1]` range before an expected object is passed over (brackets inside strings are ignored; at most 100 starting brackets are tried). Brackets nested inside a top-level value are never tried on their own: when the outer value is malformed (a trailing comma, single quotes, unquoted keys) or cut off, the node fails instead of handing on a fragment of it. A bracket that never closes ends the search when the text from it to the end is the start of a JSON value cut off by the end of the text (`["x", {"a": 1}, {"b":` fails rather than returning `{"a": 1}`); otherwise it is prose and is skipped (`[sic`, `Use { carefully`, `He said "use {"`). The flip side: a value that is both malformed and cut off (`{mood: "happy", stats: {"hp": 3}`) reads as prose, so the complete value nested in it is returned. A `number` or `boolean` must be the whole candidate (`7` or ```` ```\n7\n``` ```` is 7, `Rating: 7` and `about 7/10` fail; a number too large to hold, like `1e999`, fails too), and `text` must be a JSON string (`"hello"`). A wrong type or no value fails the node with a plain message (`Expected a number, got an object`, `No JSON value found in the text`), and the node logs the raw input (`Input: …`, cut to 500 characters) in its execution log `logs`. A value an `any` source hands over already parsed is only type-checked.

### Recall and Draw nodes

Both read **authored collections** (see Authored collections below; user guide in [docs/COLLECTIONS.md](docs/COLLECTIONS.md)) through `ctx.resources.collections`, which `prepareWorkflow` snapshots once per run like presets and providers (the server passes `CollectionRepository`). They never write them. Their `collectionIds` config lists the collections to read, in order; duplicates are read once, an empty list is a config error, and an id with no record fails the node with `Collection <id> not found. Pick another collection in the node's settings.` (a runtime error, not a validation issue). Only enabled entries with non-blank text are used. Entries are output as `{ collectionId, entryId, text, keywords, tags, title?, level? }`, where `entryId` is the entry's position (`entry-<n>`) and is not stable across edits (shared helpers in `packages/engine/src/collections.ts`).

**Recall** (category Lore) is the lorebook read: an entry is recalled when any of its keywords appears in the recent chat. It scans the last `scanMessages` history messages (default 4), the current message, and its optional `text` input (marked `neverSkips`: when that source is skipped or produced nothing, Recall still runs on the messages, even when `text` is its only connection); each text is searched on its own, so a keyword never spans two messages. Keywords are literal (regex characters match themselves), trimmed, and blank ones are ignored; entries without keywords never match. `caseSensitive` defaults to false (Unicode case folding). With `wholeWords` (default true) a keyword's edge needs a word boundary only when its edge character is a letter, mark, digit or `_` of any script, so `inn` misses `innkeeper`, `Борин` misses `Борина`, and `C++` or `#tag` still match. Letters of scripts written without spaces (Han, Hiragana, Katakana, Thai, Lao, Khmer, Myanmar) and of Hangul (Korean attaches particles to nouns: `서울에`) never count as word characters, on the keyword's edge or next to it, so `東京` matches in `私は東京に行く`, `Tokyo` in `私はTokyoに行く` and `서울` in `서울에 가요`. Other suffixing languages (Turkish, Finnish, Hungarian…) keep word edges, so their users turn `wholeWords` off; the panel says so. Matches keep collection order (config order, then file order). `maxEntries` (default 5) and `maxChars` (default 0 = no limit; the separator counts) cut the list: it stops at the first entry that doesn't fit, rather than skipping to a shorter later one, and a log line says how many were dropped. Outputs: `text` (the kept texts joined by `separator`, default a blank line; `''` when nothing matched), `entries` and `count`. The matching rules live in `nodes/recall/match.ts`.

**Draw** (category Lore) is the deck read: a weighted random pick among the entries that pass its filters. `count` (default 1) entries are drawn without replacement, one `ctx.random()` draw each, so the run seed reproduces them. Filters: `requireTags` (all of them), `anyTags` (at least one, when not empty), `excludeTags` (none of them), `minLevel`/`maxLevel` (1–5; min above max is a config error). Tags compare trimmed and case-insensitively. **When either level bound is set, entries without a `level` are left out.** With `useWeights` (default true) an entry's chance is proportional to its `weight`; off, every eligible entry has the same chance; `weight: 0` is never drawn either way. Optional inputs override the config when connected: `maxLevel` (`number`; numeric text such as an enum chat setting's `'2'` is accepted, anything else fails the node) and `tags` (`any`: a list of text or comma-separated text, replacing `requireTags`). Both are `requiredIfConnected`, so a source that was skipped skips Draw instead of drawing with the config. Outputs: `entry` (the first drawn entry), `text` (its text, or every drawn text one per line when `count` > 1) and `level` (the first drawn entry's level as a number, also absent when it has none; a preset input gets it as text, so `{{#if (eq input.level "1")}}` words one draw by its level) are **optional** ports, absent when nothing is eligible: a node that requires them is skipped, others (an LLM through a preset input) run without them; `entries` (all drawn, `[]` when none) and `reason` always come out. `reason` reads `drew 1 of 14 eligible (tags: forest; level ≤ 2)`, `drew 2 of 2 eligible (asked for 3; tags: forest)` or `no eligible entry among 20 (tags: forest; level ≤ 2)`; its parts are, in order, `tags: …`, `any tag: …`, `without: …`, the level range, `weights off`. The selection is the pure `drawEntries` in `nodes/draw/select.ts`; its `isExcluded` option is how `avoidRecent` leaves out recent draws (`nodes/draw/recent.ts`), counted in the reason as `N recent excluded`. **Avoid recent draws** (`avoidRecent`, a whole number of turns, default 0 = off): above 0, Draw leaves out the entries it drew in the last N turns of the chat and remembers what it draws as story state under its own implicit key `draws` (see Story state). An entry is identified by its collection and a fingerprint of its trimmed text, not by its `entry-<n>` id, so reordering entries changes nothing while editing an entry's text makes it eligible again. An entry drawn in turn t is recent while turn T runs when `T - t <= N` (1 = not what was drawn last turn), counting only turns that still count. Because the memory is state, deleting a reply forgets its draws. If every eligible entry is recent nothing is drawn (`entry`, `text` and `level` are absent) and `reason` reads `no eligible entry among 3 (2 recent excluded)`; `drew 1 of 2 eligible (1 recent excluded)` otherwise. With 0 the node reads and writes no state.

### Message API and partial failures

`POST /api/sessions/:id/messages` accepts `{ content }` and returns `{ userMessage?, assistantMessages: [...], execution }`. An empty `content` (or none) stores no user message: the turn runs on the session history as it is, `userMessage` is absent, and `trigger.message` is `''`. The array may be empty. Assistant messages may have `name` and `characterId`; the name is snapshotted when the message is created, so renaming a card does not rename old messages. Older stored sessions without these fields still work. Both user and assistant messages reference their execution, allowing the UI to display warnings/errors even when no output ran.

| Method and path | Request | Success |
| --- | --- | --- |
| `PATCH /api/sessions/:id/messages/:messageId` | JSON `{ content: string }`, trimmed, minimum 1 character | `200` updated message: `{ id, role, content, createdAt, executionId?, name?, characterId?, editedAt? }` |
| `DELETE /api/sessions/:id/messages/:messageId` | No body | `204` with no response body |

Both parameters are UUIDs defined in the shared contract. Missing sessions or messages return `404` with `{ error: { code: 'NOT_FOUND', message: 'Session not found' | 'Message not found' } }`; invalid parameters or content return the standard validation `400` envelope. `services/messages.ts` mutates only the targeted message under the same `sessions.update` per-session lock as sending, leaves the session's `updatedAt` unchanged (only sending a message advances it), and retains all other messages and message fields. An edit that changes the (trimmed) content stamps the message's `editedAt` (ISO time; display only: the chat's story state is never recomputed from an edit, and a save that changes nothing is not an edit). Deleting a message is content-only too, but a reply's deletion can change the story state: the fold decides from the remaining messages which turns still count (see Story state). Concurrent API mutations wait for an in-flight workflow instead of racing its write; the UI also prevents these requests while busy.

The engine returns `{ replies: Array<{ nodeId, content, name?, characterId? }>, execution, writes }`, `writes` being the story state writes of the nodes that ran (see Story state). On failure it throws `ExecutionFailure` with `.execution`, ordered `.replies` containing only completed outputs and `.writes` of the nodes that completed. Node failures also carry structured `.nodeId` and `.nodeType`; execution-wide abort/progress failures leave these undefined. The server uses this metadata, not message parsing, to label errors and keeps completed replies in the locked session before returning HTTP 500 with `{ error: { code: 'WORKFLOW_EXECUTION_FAILED', message, details: { userMessage?, assistantMessages, execution } } }`.

Error `details` uses the same shared schema as a successful message result. The chat client displays kept replies plus the error notification and execution details; named speakers show their snapshotted name and an available character avatar. Retrying sends a new user message, rather than rolling back the failed turn.

## Chat settings

**Chat settings** are knobs a workflow declares and each chat sets: a volatility dial, an "allow violence" toggle, a max-intensity choice, an author's note. They belong to the user: turns only read them, and editing, deleting or regenerating messages never changes them. Changing one is not a turn and adds no message; the next turn uses the new value.

A workflow declares them in its record (`settings`, absent in older files; read through `workflowSettings()`), edited in the workflow editor:

```yaml
settings:
  - key: volatility        # letters, digits and _, not starting with a digit; unique
    label: Volatility      # optional; the UI falls back to the key
    type: number           # number | boolean | enum | text
    default: 0.3           # number default 0, boolean false, text '', enum: the first option
    min: 0                 # number only, optional
    max: 1
    step: 0.05             # UI granularity only, never enforced on stored values
    description: How often fresh material is injected
  - key: maxLevel
    type: enum
    options: ['1', '2', '3']   # strings; compare with (eq settings.maxLevel "2")
    default: '2'
  - key: authorsNote
    type: text
    multiline: true
```

- **Validation:** a `settings` value that is not a list, a missing, unusable or reserved key (`this`, `true`, `false`, `null`, `undefined`, `toString`, `constructor`, `prototype`, `__proto__`), a duplicate key, `min` above `max`, a number default outside `min`..`max`, a `step` that is not positive, an enum without options and an enum default that is not an option are workflow issues (`workflowSettingIssues` in `@st/shared`, reported by `prepareWorkflow` in plain language), so a turn on such a workflow fails with `WORKFLOW_INVALID` like any other workflow problem. A declaration of an unknown `type` (or with a field of the wrong type) is rejected when the workflow is saved (`400`). The workflow editor never drops one it finds in a file: it shows it as a read-only row with the problem and a Remove button, and refuses to save or duplicate the workflow until it is removed or fixed in the file.
- **Values** live on the session (`settings: { [key]: value }`, `{}` for new chats, absent in older files). A key the user never set is not stored, so its declared default applies and a changed default reaches every chat that hasn't overridden it.
- **Resolving** (`resolveChatSettings` in `@st/shared`, the only place that decides): a stored value is used when it fits its declaration (right type, a finite number within `min`/`max`, one of the enum's options); otherwise the default runs and an issue is reported (`Stored value 12 is above max 10; using default 3`), shown in the chat panel and added to the turn's execution `warnings`. Stored values are never rewritten. Keys the workflow doesn't declare are kept on the session but unused, so switching a chat to another workflow and back keeps its values.
- **In a turn:** the server resolves the session's values when the turn starts (`startTurn`) and passes them to `executeWorkflow` (both the streaming and the plain endpoint). A change made while a turn streams applies from the next turn. The values the run used are recorded in `execution.settings`. Templates read them as `{{settings.<key>}}` (see `docs/TEMPLATING.md`); the **Chat Settings** node outputs them as ports.
- **Preset preview** with a `sessionId` renders that chat's resolved settings (what its next turn would see); without a session, each `{{settings.<key>}}` renders the default of the first workflow declaring that key (what a new chat would see; the same catalog as the preset editor's hints).

| Method and path | Request | Success |
| --- | --- | --- |
| `PATCH /api/sessions/:id` | JSON with any of `title`, `workflowId`, `characterId`/`personaId` (`null` clears), and `settings`: a partial map merged into the stored values, where `null` removes a key (back to its default; accepted for any key) | `200` the session. A value that doesn't fit its declaration, or a non-null value for a key the chat's workflow (after the patch's `workflowId`, if any) doesn't declare, is `400 CHAT_SETTING_INVALID` with a plain message and `details.issues: { key, message }[]`, and nothing is written. Like every metadata patch, it never advances the session's `updatedAt`. |

**Chat panel** (web): the sliders icon in the chat header ("Chat panel", usable while a turn runs) toggles `ChatPanel`, a side panel inside the chat view (not a layout view). It has a Settings section (below) and a Story state section (see Story state in the web). Its Settings section (`pages/chat/panel/`) shows one control per setting the chat's workflow declares: a slider plus a number field for a number with both `min` and `max`, a number field otherwise (partial input such as `-` stays editable; an invalid number shows why and is not saved, and cancels the pending save of an earlier valid prefix, e.g. the `1` of `12` above max 10), a checkbox, a dropdown, a text field or a textarea for `multiline` text. It shows the stored value or the default, the setting's description, the resolver's issue for a stored value the workflow no longer accepts, and a reset button (back to the default, `null` in the PATCH) when a value is stored. Checkboxes and dropdowns save at once; typed values and slider moves save after a 500 ms pause, on blur, or when the panel closes (`saveMode` and `createSettingSaver`, tested with fake timers), through `sessionsApi.update`. The saver keeps one request in flight and sends values that came due meanwhile together in the next, so answers arrive in order and each holds every earlier write; when the page is hidden for good (`pagehide`: reload, tab close) it sends whatever is left at once with `keepalive`. `useChat.updateSettings` applies only `settings` from each answer (`withStoredSettings`: the stored session may hold rows of a streaming turn), and header patches keep the local settings (`withStoredMetadata`), so a change made while a turn streams never disturbs it and applies from the next turn. A key declared twice gets one control (its first declaration, as the resolver reads it). When the workflow declares nothing, the panel says so and links to it in the workflow editor. In a chat column narrower than 760px (a phone, or the chat in R next to a wide editor) the panel covers the messages; the chat view is the `chat` CSS container. Execution details list the settings a turn used.

Workflow `settings` travel in the workflow record: `PUT /api/workflows/:id` replaces them when the body has `settings` and keeps the stored list when it doesn't; `POST /api/workflows` accepts them so a duplicate keeps its declarations.

## Presets and LLM providers

A **preset** defines the final, ordered message list sent to an LLM. It has declared **inputs** (the values a workflow supplies) and an ordered list of discriminated **entries** (`message` or `slot`) that assembles those values with fixed prompts. Each input has an `id`, unique key, optional label and description, and type (`messages` or `text`). Every input becomes one correspondingly typed LLM input port named by its key; the port label defaults to the key. A `messages` input expands to its message list. A `text` input becomes one message using the slot's role (default `user`) and is skipped when empty. The same input may be placed by multiple slots.

An enabled **message** entry has a system/user/assistant role and templated content; it can use `{{input.<key>}}`, `{{trigger.message}}`, `{{trigger.sessionId}}`, `{{history}}`, and character/persona variables. Character and persona fields are also expanded when referenced, with recursive references guarded. Missing character fields render as empty text; `{{user}}` falls back to `User`. Every entry has a required `displayName`, the label shown in the editor. A message entry may also have an optional `name`: a template rendered with the same context as the content, trimmed, and sent as the prompt message's `name` only when non-empty (an entry whose content renders empty is still dropped). Its unknown `{{input.x}}` references are errors, and syntax problems and unknown macros are warnings, exactly like content; an input referenced only by a name counts as used. A **slot** places a declared input at its position in the final message list. Fixed messages that render to whitespace only are omitted, as are empty text-slot values. Inputs unused by any enabled slot or message template produce non-blocking warnings. Model and sampler settings belong to each LLM node. Preview and execution use the same renderer, and the preview accepts `{ preset, inputs?, sessionId? }` and returns `{ messages, warnings }`.

Preview `inputs` accepts strings for text inputs and arrays of `{ role, content, name? }` for messages inputs. Explicit messages arrays are used unchanged by the preview, including an empty array; only an omitted messages input falls back to the selected session's history or the sample conversation. The current preview UI still selects session/sample history rather than editing messages arrays.

The **Default** preset declares `history` (`messages`, label “Chat history”) and `message` (`text`, label “User message”). Its ordered system entries are Main prompt (a short instruction plus `{{character.system_prompt}}`), Character description, Personality, Scenario, Persona (`{{persona.description}}`), and Example dialogue; then the history slot; then Post-history instructions; then the user-message slot. Each character/persona field is a separate variable-only entry, so empty fields produce no blank prompt messages. The character's first greeting is not included. The Default Assistant workflow connects Chat Input `history` and `message` to those LLM ports.

## Importing presets from other apps

Connectors copy content from another app's install folder into local records. Each connector has one config record, keyed by its app id (`sillytavern` is the only one so far). Adapters live in `apps/server/src/services/import/` (`connector.ts` defines the shape: detect, scan, name, map). Sync, routes and the config are generic over that shape.

| Method and path | Request | Success |
| --- | --- | --- |
| `GET /api/import-sources` | none | `ImportSource[]`: `{ id, app, path, lastSyncAt? }` |
| `PUT /api/import-sources/:app` | JSON `{ path }` (trimmed, required) | `200` the stored record. The path is resolved to an absolute path and must hold a `data/` folder, or the response is `400 IMPORT_SOURCE_INVALID`. |
| `POST /api/import-sources/:app/sync` | No body | `200` `{ created, updated, unchanged, missing }`. `409 IMPORT_SOURCE_NOT_SET` when no folder is configured; `400 IMPORT_SOURCE_INVALID` when the folder has gone. |

SillyTavern presets are read from `<install>/data/<user>/OpenAI Settings/*.json` for every user folder, skipping folders whose name starts with `_`. Nothing else in the install is read: symlinks and nested folders are not followed, and files over 5 MB are skipped. A file's identity is (install path, user, file name). Its preset name is the file name without `.json`, plus ` (<user>)` unless the user is `default-user`.

Each sync works like this:
- A file with no record creates a preset.
- A file whose hash changed overwrites its preset in place, keeping the preset id, so workflows stay linked. Edges into inputs that no longer exist are pruned, as preset `PUT` does. The hash is the sha256 of `mapper <version>\n` followed by the file bytes. Each connector sets `mapperVersion`; bumping it re-imports every file on the next Sync, so mapping fixes reach existing presets. The SillyTavern connector is at version 2.
- An unchanged file is left alone, including its `updatedAt`.
- A preset whose file is gone is kept and marked `source.missing: true`. The flag is cleared if the file returns. Its `updatedAt` does not change.
- An unreadable, invalid or oversized file is skipped with a server warning. Its local copy stays, and it is not counted.
- Syncs are serialized per connector (`context.importLock`). Presets from another install folder are never touched.

Imported presets carry an optional `source` (`presetSourceSchema` in `@st/shared`): `{ app, installPath, user, file, hash, importedAt, missing? }`. The field belongs to the server:
- `POST /api/presets` and `PUT /api/presets/:id` strip any client-sent `source`, so a duplicate is always an editable copy.
- `PUT` on a preset with a `source` fails with `409 PRESET_READ_ONLY` and leaves the record unchanged. `DELETE` still works, and the next sync recreates the preset.

In the web app, Settings → **Import content** saves the SillyTavern install folder (the one containing `data/`) and runs **Sync**. Sync stays disabled until a folder is saved; the counts appear in a toast and the last sync time is shown under the folder. On the Presets page, imported presets carry an *imported* badge (or *source missing* when `source.missing` is set). Opening one shows a banner with its origin and a *Duplicate to edit* action. Name, description, inputs, entries and Save are all disabled, and entries can still be selected and previewed. The read-only state is one `readOnly` prop threaded from `pages/Presets.tsx`, and `change`/`save` also ignore edits for imported presets. Duplicating (from the list or the banner) builds the create body without `source`, so the copy is editable.

### SillyTavern chat-completion mapping

`apps/server/src/services/import/sillytavern-mapper.ts` is a pure function from parsed JSON to inputs and entries.
- Order: the `prompt_order` entry with `character_id` 100001 is used, then 100000, then the first entry. Only the identifiers listed there are imported, in that order, with `enabled` taken from the order entry. Anything absent is ignored.
- A normal prompt becomes a `message` entry. The role is `system` when it is missing or unknown. The content is kept verbatim, macros included, so unsupported macros show up as preset warnings. Its label (`displayName`) is the prompt name, falling back to its identifier; no message `name` is set.
- `chatHistory` becomes a `messages` input named `history` plus a `slot` entry. A `message` text input and a `Current message` slot follow it (enabled together), because a turn's history is captured before the new user message is saved.
- `charDescription`, `charPersonality`, `scenario`, `dialogueExamples` and `personaDescription` become system messages with `{{character.description}}`, `{{character.personality}}`, `{{character.scenario}}`, `{{character.mes_example}}` and `{{persona.description}}`.
- `worldInfoBefore`, `worldInfoAfter` and any other marker become disabled, empty `message` entries named after the marker.
- Absolute injection (`injection_position: 1`) with an `injection_depth` N is counted like ST, from the end of the chat including the new user message. Our history slot excludes that message, so for N >= 1 the entry gets depth N-1 in the first enabled chat-history slot. Depth 0 cannot be expressed as history depth, so it stays ordered and is moved to sit right after the `Current message` slot. Without an enabled chat-history slot, every prompt stays ordered where the prompt order lists it. `injection_order`, sampler settings and other top-level fields are ignored.

## Characters and Personas

Characters and personas are managed from the top-level **Characters** and **Personas** pages. Character cards store name, description, personality, scenario, first message, example dialogue, system and post-history prompts, alternate greetings, tags, creator metadata, extensions, and an optional avatar. The editor keeps the commonly used name, description, and personality fields prominent and places the rest under Advanced fields. Persona records contain a name, description, and optional avatar. JSON and avatar files are stored below `data/characters`, `data/personas`, and `data/avatars/`; uploads are limited to 20 MB per file.

Character JSON cards may be flat V1, V2 (`spec: "chara_card_v2"`), or V3 (`spec: "chara_card_v3"`). PNG cards are parsed and exported server-side using `chara` and `ccv3` tEXt metadata; when both exist, V3 is preferred. PNG character imports require embedded card metadata, while plain persona images create a persona named from the file name. PNG exports include both V2 and V3 card metadata and use the stored avatar or a generated placeholder.

The REST API exposes:

| Method and path | Purpose |
| --- | --- |
| `GET/POST /api/characters` | List or create a character |
| `GET/PUT/DELETE /api/characters/:id` | Read, update, or delete a character |
| `POST /api/characters/import` | Import one or more JSON cards or PNG cards as multipart files |
| `GET/PUT /api/characters/:id/avatar` | Retrieve or upload the character avatar |
| `GET /api/characters/:id/export?format=json\|png` | Export a character card |
| `GET/POST /api/personas` | List or create a persona |
| `GET/PUT/DELETE /api/personas/:id` | Read, update, or delete a persona |
| `POST /api/personas/import` | Create personas from uploaded images (embedded card metadata is used when available) |
| `GET/PUT /api/personas/:id/avatar` | Retrieve or upload the persona avatar |

Import endpoints return `{ imported, failed }` for multi-file uploads and use the standard `{ error: { code, message, details? } }` API error shape for invalid requests. Sessions store optional `characterId` and `personaId`; selecting them in Chat persists the context used by preset and node templates. New chats select the first available persona when one exists.

Character/persona edits, avatar uploads and deletion share the repository's per-entity lock, so an avatar upload cannot overwrite a concurrent edit or resurrect a deleted entity. Avatar file work stays inside that lock. `services/entity-mutations.ts` owns these operations; plain repository `save` is used only for creation in these routes. Repository `delete` accepts an optional `beforeDelete` callback for related cleanup under the same lock. These locks are non-reentrant: callbacks must not call `update` or `delete` for the same entity.

### Template macros

The registry in `@st/shared` is the single source for engine resolution, preset validation, and editor hints. Preset entries and common node templates support:

- `{{character.<field>}}`: `name`, `description`, `personality`, `scenario`, `first_mes`, `mes_example`, `creator_notes`, `system_prompt`, `post_history_instructions`, `creator`, and `character_version`.
- `{{persona.name}}` and `{{persona.description}}`.
- Short aliases: `{{char}}` → character name, `{{user}}` → persona name (or `User` when no persona is selected), `{{description}}`, `{{personality}}`, `{{scenario}}` → matching character fields, and `{{persona}}` → persona description.
- `{{settings.<key>}}`: the chat's value of a chat setting the workflow declares (see Chat settings); `{{settings}}` renders them all as JSON. Any `settings.*` path is a known macro, so it never draws an "Unknown macro" warning; editor hints list the declared keys (the open workflow's in node panels, every workflow's in the preset editor).
- `{{state.<definition>.<key>}}`: the chat's story state as the turn started (see Story state); `{{state}}` and `{{state.<definition>}}` render as JSON, collections iterate with `{{#each}}`. Any `state.*` path is a known macro, so an unknown definition or key renders empty without a warning. `{{trigger.turn}}` is the number of the turn being run (1-based; empty when a run has no story state). Editor hints for the keys come from `stateHints` (the third argument of `macroHints`); the preset editor and the template fields of node panels (`NodePanelContext.stateDefinitions`) both build them from the definitions store, so a new key is suggested as soon as it is saved.
- `{{input.<key>}}` (or `{{inputs.<key>}}`), `{{trigger.message}}`, `{{trigger.sessionId}}`, and `{{history}}`. Node scope roots (`input`, `inputs`, `trigger`) and nested paths remain supported; preset message inputs/history render as transcripts, while node templates use JSON for structured values.

Names are **case-sensitive**, matching Handlebars: `{{CHARACTER.Name}}` and `{{INPUT.MyKey}}` are unknown and render as empty text (preset validation warns about them). Input keys that differ only by casing are still rejected in presets. Slots and port bindings use declared keys exactly.

Unknown names render as empty text and produce a non-blocking warning in enabled preset messages. Known macros without a value render as empty text (only `{{user}}` has the `User` fallback). Unknown `{{input.x}}` references remain validation errors, including inside blocks and subexpressions. Character and persona fields can contain templates themselves, expanded recursively with cycles resolving to empty text. `{{char.*}}` and `{{user.*}}` are no longer supported; use `character.*` and `persona.*`. Legacy `<BOT>`/`<USER>` and SillyTavern scripting macros are not supported.

#### Template syntax

Templates are [Handlebars](https://handlebarsjs.com/) with stock semantics and `noEscape`, so values are inserted as written. The `handlebars` runtime (parser and compiler) is a dependency of `@st/engine`, and renders presets and template-taking node configs (LLM, Chat Output, HTTP Request, Condition). `@handlebars/parser` is the only dependency of `@st/shared`, so the web bundle has no compiler; validation walks its AST.

- **Paths** are case-sensitive: `{{character.name}}`, `{{input.key}}`, `{{inputs.key.nested}}`, `{{trigger.message}}`, `{{history}}`. A numeric segment at the end of a path is a syntax error, so write `{{history.[0]}}`; `{{history.0.content}}` is fine.
- **Blocks:** `{{#if x}}…{{else}}…{{/if}}`, `{{#unless x}}`, `{{#with x}}`, and `{{#each history}}…{{/each}}` with `this`, `@index`, `@first`, `@last` and `../` (parent context). Block-only lines are removed from the output. `{{#each}}` over a missing or non-array value renders its `{{else}}` branch, or nothing, and never fails.
- **Helpers:** `eq`, `ne`, `lt`, `lte`, `gt`, `gte`, `and`, `or`, `not`, used as subexpressions, e.g. `{{#if (eq character.name "aeaze")}}`; and `linked`, which takes a collection value and gives its intact message-linked items in chat order (`{{#each (linked state.memory.summaries)}}{{text}}{{/each}}`, see Message links and summaries; anything that is not a list gives an empty one). `eq` is strict `===` and case-sensitive: `1` does not equal `"1"`, and `"Mira"` does not equal `"mira"`. `ne` is its negation. `lt`, `lte`, `gt` and `gte` use JavaScript's operators. Helpers are defined in `packages/engine/src/template-helpers.ts` and listed in `templateHelperNames` in `@st/shared`. Handlebars' stock `log` helper is removed.
- **Truthiness** (`#if`, `unless`, `and`, `or`, `not`): `false`, `0`, `""`, `null`, `undefined` and empty arrays are false. Everything else is true, including the string `"false"`.
- **Comments:** `{{! note}}` and `{{!-- note --}}` are removed.
- **Bare names:** in presets, `{{history}}` renders a `role: content` transcript and `{{input.x}}` renders message lists as transcripts and objects as pretty JSON. In node templates they render compact JSON. `{{input}}`/`{{inputs}}` render the inputs object (pretty JSON in presets, compact JSON in nodes), and `{{trigger}}` renders compact JSON. `{{#each history}}` and `{{#each input.x}}` iterate the raw messages (`this.role`, `this.content`, `this.name`). `{{persona}}` renders the persona description, and `{{persona.name}}` still resolves.
- **Errors never throw.** A template that does not parse, or uses unsupported syntax (partials `{{> x}}`, decorators, an unknown helper with arguments such as `{{foo bar}}`, or `#if` without exactly one argument), renders verbatim, unchanged. Preset validation reports it as a warning. Code-like expressions such as `{{input.x.constructor()}}` are syntax errors, so the whole template renders verbatim. A backslash before `{{` (\{{) produces a literal `{{`.

Message placement defaults to **ordered**, at its position in the entry list. **Depth** placement references an enabled slot entry backed by a `messages` input and injects the message inside that slot's expanded conversation: depth 0 inserts *after* the last message, depth 1 inserts *before* the last message, and depths beyond the slot length clamp to the start. For example, history `[user: Hello, assistant: Hi]` plus a system note at depth 1 produces `[user: Hello, system: Note, assistant: Hi]`. Messages at the same depth preserve their order in the preset entry list. Changing/removing an input can make stale workflow edges invalid (shown red); validation catches stale handles.

The LLM node selects a **provider**, **model**, **preset**, temperature, max tokens and optional samplers (top-p, frequency/presence penalties, stop sequences). History is only supplied through a preset slot; it is never added implicitly. Its outputs are `text` and `raw`. Each execution log records the node's **wire exchange** (`nodes[id].wire`, see Providers below): the URL, headers with credentials redacted, the exact JSON body sent, and the response, so provider mappings can be debugged. Logs written before the wire log keep the app's canonical request under `request`; the chat's execution details show `wire` when present and fall back to `request`.

**Merge consecutive system messages** (`mergeSystemMessages`, default `false`) is an LLM node checkbox. When enabled, after preset rendering it joins each consecutive run of system messages without a `name` using `"\n\n"`. User/assistant messages and named system messages break a run and remain unchanged (even an explicitly empty name is treated as set). Request logs contain the actual merged messages sent to the provider. Preset preview remains the unmerged preset output because merging is a node-level setting.

Chat history and message inputs carry an optional string `name`, and so do preset message entries (rendered from their `name` template). Chat Input, Memory in `messages` format, preset history previews and message slots preserve it (including through depth insertion and repeated slots); The provider adapter forwards it only when present, under the record's `messageName` field (or drops it when that is `null`). No speaker-name prefix is added to message content. A future per-slot option may control such prefixing; currently speaker names are metadata chosen through Chat Output.

Seeding uses stable IDs so concurrent initializers do not create duplicate Default presets or demo workflows. Seeds are added only when the corresponding store is empty.

### Providers

User guide with examples: [docs/PROVIDERS.md](docs/PROVIDERS.md).

A **provider record** says how to reach one OpenAI-compatible backend (OpenRouter, OpenAI, DeepSeek, Ollama, LM Studio, vLLM, ...). Records are data, not code; the design is in PLAN.md ("user-defined LLM providers"). The LLM node's `provider` config holds a record id.

| Field | Meaning |
| --- | --- |
| `id` | UUID for user records; the built-in one is `openrouter`. |
| `name` | Label shown in the node's provider dropdown; the file is named after it. |
| `kind` | `openai-compatible` (the only wire protocol today; default). |
| `baseUrl` | `http(s)://` URL; requests go to `<baseUrl>/chat/completions`. |
| `secret` | Optional name of a secret in the encrypted store. Without it no `Authorization` header is sent (local servers). |
| `headers` | Extra request headers (default `{}`). |
| `messageName` | Wire field carrying a message's `name`; `null` = never send it (default `name`). |
| `reasoningFields` | Fields read for the reasoning trace, first non-empty wins (default `[reasoning, reasoning_content]`). |
| `extraBody` | Merged into the request body last (default `{}`). |
| `overrides` | `[{ match, messageName?, reasoningFields?, headers?, extraBody? }]`: first entry whose `match` glob fits the model id replaces those fields (`headers` and `extraBody` are shallow-merged). |

Status: records, storage, API, resolution, the record-driven adapter, the wire log, live reload and the provider UI are done.

**Provider UI** (`apps/web/src/pages/providers/`): the Providers icon in L lists the records (built-ins first, from `providersStore`, which re-fetches on `providers.changed`; the LLM node's provider dropdown reads the same store). Picking one opens the narrow editor in L (`left=provider:<id>`):
- A form for `name`, `baseUrl`, `secret` (a free text field that suggests the secret names saved in Settings and warns when the name is not among them; empty means no secret), message names ("Send as a message field" with the field name, or "Don't send names" = `messageName: null`) and `reasoningFields` as an ordered list.
- One raw YAML box for `headers`, `extraBody` and `overrides`. Other keys are rejected; a missing or empty key is saved as empty (`{}`/`[]`), because PUT keeps stored fields that a body omits.
- Save validates the draft with `providerFieldsSchema` first and lists the problems above the form (`YAML overrides.0.match: …`, `Base URL: …`); server errors toast as usual. The pure draft/body logic is `providerDraft.ts`.
- The built-in provider opens read-only (the whole form is a disabled `fieldset`) with only **Duplicate**. Duplicate copies the *saved* record, so it is disabled while the draft has unsaved changes.
- Delete of a provider that LLM nodes use is refused by the server (`PROVIDER_IN_USE`); the editor shows a "Provider in use" error naming the workflows.
- Live sync follows the presets rules through the shared `startFileLiveSync` (`pages/fileLiveSync.ts`): a clean editor reloads, a dirty draft is never replaced (one warning; saving overwrites), invalid files get one persistent warning each. Records are compared through their drafts (key order and timestamps never count), and a dirty draft that the disk already holds (the editor's own save, announced before its response) counts as a reload, not a conflict.

- **Adapter** (`providers/openai-compatible.ts`, export `openaiCompatible`): one generic adapter for every `openai-compatible` record. Per request it resolves the record's wire settings for the model (`resolveWireSettings` in `providers/wire-settings.ts`):
  - **Overrides:** the first override whose `match` fits the model id wins. `match` is a case-sensitive glob over the whole id; `*` is the only wildcard and also matches `/`. It replaces `messageName`/`reasoningFields` (an explicit `messageName: null` drops names) and shallow-merges `headers`/`extraBody` over the provider's.
  - **Request:** `POST <baseUrl>/chat/completions` with `Authorization: Bearer <secret>` only when the record names a secret, then `Content-Type`, then the resolved `headers`. A message's `name` is written to the `messageName` field when set (an empty name counts as set) and never sent when it is `null`. Samplers keep their OpenAI names, and reasoning options go out as OpenRouter's `reasoning` object (`effort`, `max_tokens`, `exclude`) for every record. `extraBody` is spread over the body last, so it can override any computed field (`reasoning: null` sends a JSON `null`; it cannot remove a key). Overriding `stream` breaks streaming parsing.
  - **Response:** the reasoning trace is the first non-empty `reasoningFields` entry on each stream delta, or on the non-stream `choices[0].message`. Both modes return it as `ChatResponse.reasoning`. The streamed `raw` mirrors a non-stream response and reports it as `message.reasoning` whichever wire field it came from; the non-stream `raw` is the upstream JSON unchanged. The LLM node surfaces reasoning as `reasoningDelta` events: per chunk while streaming, and as one delta with the whole trace after a non-stream call. Either way it reaches the chat only through the streaming endpoint and only for passthrough Chat Outputs (LLM `text` straight into `value`); the plain `POST .../messages` endpoint and templated outputs do not store it.
  - Idle timeout (120 s between stream chunks, 600 s for a whole non-stream request), abort handling and error parsing (`<provider name> <status>: <message>`) are shared by all records. A non-JSON `200` response fails with `<provider name> returned a response that is not JSON`.
  - **Wire log:** the adapter reports each request through the optional `onWire` callback in `ChatOptions` (the LLM node passes `ctx.recordWire`, which writes `nodes[id].wire`). It reports once before `fetch` (`{ url, method, headers, body }`) and again with `status` and `response` once known, each report replacing the last, so a failed or timed-out call still shows what was sent. `body` is the object that was serialized for `fetch`. `response` is the parsed JSON (or the text, truncated to 2000 characters, when it is not JSON), including error responses; for streams it is the chunks folded into one object under the backend's own field names (string fields of `delta` concatenated, e.g. `reasoning_content`), recorded also when a stream fails midway. It is not the node's `raw` output, which keeps its mapping-independent shape. Redaction happens inside the adapter (`providers/wire-log.ts`) before the callback: headers whose name matches `auth|key|token|secret|cookie|password` are masked (an auth scheme stays visible: `Bearer [redacted]`), and the secret value is replaced wherever it appears in the report and in the adapter's error messages (a backend may echo the key back in an error). Values typed into a record's `baseUrl` or `extraBody` are record data, not secrets, and are logged as sent.

- **Model lists** (design in PLAN.md, "provider model catalogs"): the app learns what a provider serves through the optional `listModels({ provider, apiKey?, signal })` of its adapter (`LlmAdapter` in `providers/index.ts`). The `openai-compatible` one (`providers/openai-models.ts`) does `GET <baseUrl>/models`, the de facto `{ data: [{ id, ... }] }` endpoint, with the chat rule for auth (Bearer only when the record names a secret) and the record's top-level `headers` (override headers are per model, so they are not sent). One generic path reads every backend: `normalizeModels` (`@st/shared`, `provider-models.ts`) keeps `id`, `name`, `description`, `contextLength` (`context_length`), `maxOutputTokens` (`top_provider.max_completion_tokens`), `inputModalities`/`outputModalities` (`architecture.*`), `supportedParameters` and `pricing` (`prompt`/`completion`, USD **per token** as numbers; zero is kept, missing, blank, non-numeric and negative values such as OpenRouter's `-1` are dropped) when the entry carries them. Entries without a string `id` and repeated ids are skipped, unknown fields ignored, and a payload without a `data` array is an error (an empty array is a valid, empty list). The request is bounded by a 30 s timeout; errors name the provider (`<name> 401: ...`, `<name> could not be reached: ...`) and never contain the key (`withoutSecret`). The missing-secret text is shared with the LLM node (`missingSecretMessage`).
- **Model catalog (server):** `GET /api/providers/:id/models` goes through `ModelCatalog` (`services/provider-models.ts`, on the app context) so the key never reaches the browser. Lists are cached in memory only, per provider id, for 1 h. An entry is stale as soon as the whole provider record changes (compared as a fingerprint of the record, not `updatedAt`, because a file edited on disk keeps its old timestamp) or any secret is written or deleted (`SecretStore.revision`). Concurrent requests for the same provider and version share one fetch, which is bounded only by the adapter's timeout (no request signal, so one client leaving cannot abort the others). Failures are never cached. `?refresh=true` skips the cache. A restart refetches on demand.
- **Built-in providers** (`builtInProviders` in `@st/shared`) are defined in code and read-only: OpenRouter (id and secret `openrouter`, so existing nodes and the existing secret need no migration) and abliteration.ai (id and secret `abliteration`). They are listed first, in array order, with `builtIn: true`; `PUT`/`DELETE` on it answer `409 PROVIDER_READ_ONLY`. A stored file claiming a built-in id is invalid (user ids must be UUIDs).
- **Storage:** `data/providers/<slug-of-name>.yaml` through `ProviderRepository`, the same `YamlRepository` as presets (see Preset files: identity is the `id` inside the file, nothing cached, invalid files skipped with a warning and never modified, a hand-written file without `id`/timestamps is stamped once, atomic writes under an id lock). Keys are written in the order `name, kind, baseUrl, secret, headers, messageName, reasoningFields, extraBody, overrides, …, id, createdAt, updatedAt`. **Live reload:** `data/providers/` is watched like the preset directory (same `watchDirectory`, started only from `main.ts`), and every API write (create, update, delete, duplicate) also publishes `providers.changed` from `services/providers.ts`, so clients update even without a watcher. Both carry the files that currently fail to load (`invalidFiles`, always from a fresh scan); with the watcher on, an API write is announced twice, which is harmless.
- **Resolution:** `prepareWorkflow` snapshots provider records into `resources.providers` (built-in ids resolve in the engine, everything else through the `providers` resource the server passes). The LLM node reads its record from `ctx.resources.providers`; an unknown id is a node error `Unknown LLM provider: <id>`, and a record whose `secret` is set but missing fails with `Missing <secret> secret. Add it in Settings.` The adapter for the record's `kind` (`adapters` map, `LlmAdapter` in `providers/index.ts`) receives the record in its options: `chat(request, { provider, apiKey?, signal })`, and `stream(...)` with `onToken`/`onReasoning` in addition. Tests swap the `openai-compatible` adapter (`useAdapter` in `test-providers.ts` / `test-support/adapter.ts`).

| `GET /api/providers/:id` | `200` one record (the id may be `openrouter`); `404`. |

## Authored collections

An **authored collection** is a list of entries the user writes (a lorebook, a deck of story textures). Workflows only read collections; no node writes them. User guide: [docs/COLLECTIONS.md](docs/COLLECTIONS.md).

- **Schema** (`packages/shared/src/collection.ts`, `passthrough` at both levels so imported formats round-trip): a collection has `name`, optional `description` and `entries`; an entry has `text` (required, may be multi-line), optional `title`, `keywords`, `tags`, `level` (integer 1–5), `weight` (number ≥ 0, default 1) and `enabled` (default true). Collections are read through the YAML codec, which parses every file on read, so `.default()` is safe for them (unlike JSON records).
- **Entry ids are derived, not stored:** `collectionEntryId(index)` gives `entry-<n>` (1-based position). Reordering or inserting entries changes them, so nothing may rely on an entry id surviving a save. An `id` key written in a file is an unknown field: kept, never read.
- **Storage:** `data/collections/<slug-of-name>.yaml` through `CollectionRepository` (`storage/collection-repository.ts`), the same `YamlRepository` as presets and providers (identity is the `id` inside the file, nothing cached, invalid files skipped with a warning and never modified, a hand-written file without `id`/timestamps is stamped once, renames follow the name). Keys are written in the order `name, description, entries, …, id, createdAt, updatedAt`, entry keys as `title, text, keywords, tags, level, weight, enabled, …`; multi-line text is a literal block scalar, and the default values `weight: 1` and `enabled: true` are left out. Null values (`title:` with nothing after it) make the file invalid, and an invalid file is never stamped: only a blank `id`/`createdAt`/`updatedAt` counts as missing (`parseYamlRecord` in `storage/yaml-record.ts`, shared with providers), so `description:` left blank keeps an id-less file invalid and untouched. Like every YAML repository, `get` rescans the directory, so a turn reads the directory once per collection it uses (each is cached for the rest of the run).
- **Live reload:** `data/collections/` is watched like the preset directory, and every API write also publishes `collections.changed` (`services/collections.ts`, always with a fresh `listInvalid()`).
- **Collection UI** (`apps/web/src/pages/collections/`): the Collections icon in R (Library) lists the summaries from `collectionsStore` (by name, re-fetched on `collections.changed`; the Recall and Draw node panels read the same store), with a search box and **+ New**. Picking one opens the narrow editor in R (`right=collection:<id>`): `openCollection` (`collectionActions.ts`, also used by the node panels' Edit link) fetches the whole collection with `GET /api/collections/:id` first and only then switches the editor, so the previous collection is never shown while loading and the URL changes once; only the latest click applies. A URL naming a collection opens it through the editor store with a summary; the editor then clears at once and loads it. The editor has name, description and the entries as an accordion: each row shows the title (or the first line of the text) with badges (level, keyword and tag counts, disabled) and move up/down/delete buttons; the open row shows text, title, keywords and tags (comma-separated), level (none or 1–5), weight and enabled. Keywords, tags and weight stay text in the draft (`collectionDraft.ts`) and are converted and checked on save; a list whose text was not edited is sent back as stored, so a keyword holding a comma survives. Unknown entry fields are sent back unchanged. Save, Discard (while dirty) and Delete (with confirmation; `409 COLLECTION_IN_USE` is shown with the workflow names). Discard re-reads the collection before resetting, so a disk edit that arrived while the draft was dirty is what it returns to (a collection gone from disk closes). A save answered `404` asks first (`window.confirm`) and only then recreates the draft as a new collection: the server also answers `404` while the file exists but no longer parses (invalid files are skipped), and a new record would leave the nodes on the old id; declining keeps the draft so the file can be fixed. Save is disabled while a save is in flight, so a double click never creates two. The name is sent trimmed, as the server stores it. Entry rows are memoized and the dirty check normalizes the stored side once per load, so typing stays quick in lorebooks of hundreds of entries. Live sync (`startFileLiveSync`) re-reads the open collection on every `collections.changed` (hand edits keep `updatedAt`, so summaries cannot reveal them): a clean editor reloads keeping the open entry by position, a dirty one gets one warning ("removed from disk or can no longer be read": both look the same to the client), a deleted one closes, and invalid files show one persistent warning each.

| --- | --- |

| `GET /api/collections/:id` | `200` the full record; `404`; `400` when the id is not a UUID. |
| `POST /api/collections` | Body: `name`, optional `description`, `entries` (required: a write replaces them, so a body without them is a `400`, never an erased list; `collectionWriteSchema`). `201` the stored record. Client bookkeeping (`id`, timestamps, `entryCount`) is ignored. |
| `PUT /api/collections/:id` | Same body; replaces name, description (an omitted one is removed) and entries; unknown stored top-level fields survive. `404`. |
| `DELETE /api/collections/:id` | `204`; `409 COLLECTION_IN_USE` (details: workflow names) while a Recall or Draw node lists it. |

## Story state

**Story state** is what a chat remembers between turns: numbers, flags, moods, notes and lists that workflow nodes write and later turns read (pacing, what was just drawn). It belongs to one chat and lives exactly as long as the replies of the turns that wrote it: delete a reply and what its turn stored is undone. A **state definition** names and types the keys; nodes (State Read, State Write, Draw's `avoidRecent`) and templates (`{{state.*}}`) use them. The model is in `packages/shared/src/state/`; the engine side is `StateWriteBuffer`, `ctx.state` and `ctx.writeState`; the server folds, stores and serves it.

### State definitions

A definition is a YAML file under `data/state/definitions/<slug-of-name>.yaml` (`StateDefinitionRepository`, the same `YamlRepository` as presets, providers and collections: identity is the `id` in the file, nothing cached, invalid files skipped with a warning and never modified, a hand-written file without `id`/timestamps stamped once). The seed is one example, `scene`, created only into an empty directory (no definition and no invalid file), so it never overwrites anything and does not come back once the user has definitions of their own:

```yaml
name: scene
description: Pacing state for the creativity pipeline
keys:
  tension:
    type: number
    default: 3
    min: 0
    max: 10
  mood:
    type: enum
    options:
      - calm
      - uneasy
      - tense
      - release
    default: calm
  lastInjectionLevel:
    type: number
  injected:
    type: collection
    cap: 30
    fields:
      level: number
      entryId: text
id: 8d1f6a42-3c5e-4b7a-9e21-5f0c7a1d9b34
createdAt: 2026-01-01T00:00:00.000Z
updatedAt: 2026-01-01T00:00:00.000Z
```

| Key type | Fields | Reads as when nothing (valid) was written |
| --- | --- | --- |
| `number` | `default`, `min`, `max` | `default`, else 0 (kept within min and max) |
| `boolean` | `default` | `default`, else `false` |
| `enum` | `options` (at least one, text; quote numeric ones), `default` | `default`, else the first option |
| `text` | `default` | `default`, else `''` |
| `object` | `default`, `schema` (kept, not checked yet) | `default`, else `{}` |
| `collection` | `cap` (whole number from 1), `fields` (`text`, `number` or `boolean` per extra item field; `id` and `text` always exist) | `[]` |

Definition and key names are template path segments (`{{state.scene.tension}}`): letters, digits and `_`, not starting with a digit, and not a reserved word (`this`, `true`, `false`, `null`, `undefined`, `toString`, `constructor`, `prototype`, `__proto__`). Definition names are unique, compared ignoring case (`409 STATE_DEFINITION_NAME_TAKEN`; file names are lower-cased). A hand-edited file that repeats a name is not refused: the oldest definition (`createdAt`, then `id`) keeps the name in templates, and every run says so in its execution `warnings`. Unknown fields at both levels are kept (`passthrough`). Number bounds that contradict (`min > max`, a default outside them), an enum default that is not an option, repeated options and collection fields named `id` or `text` make a definition invalid, with the key named in the reason.

Changing keys or types is always allowed: stored data is never rewritten, the fold just reads a value that no longer fits as the default (see below). The workflows that use the definition are looked after on save, like a preset edit does for its inputs: connections to ports that no longer exist (State Read's `count` once the key stopped being a collection) are dropped, nodes never are. A State node whose key is gone, or whose operation no longer suits the key's type (`increment` on a key that became text), keeps its connections and shows up in validation as a plain issue naming the node, `WORKFLOW_INVALID` on the chat's next turn, until it is pointed at a key that exists; the stored data stays, so restoring the key brings the chat back as it was. The one thing that can't change under data is the **name**: a rename is refused with `409 STATE_DEFINITION_IN_USE` while any chat has live data under it, because templates address it by name; duplicate the definition to use another name. (Nodes address a definition by id, so a rename never breaks a workflow.) Deleting is refused the same way, and also while a State Read or State Write node of any workflow uses it (otherwise the chat's workflow would become invalid). "Live" means a turn that still counts wrote it (a chat whose replies were deleted holds dead data that can never come back, so it does not block). `details` is `{ sessions: { id, title }[], workflows: string[] }`, either list possibly empty; the message names at most five of each.

**The editor** (`pages/stateDefinitions/`, in L like the provider editor). The list (`StateDefinitionListView`) reads `stateDefinitionsStore`, which holds whole records and re-fetches on `stateDefinitions.changed`; "+ New" creates `new_state` (or the first free `new_state2`, `new_state3`…). The editor edits a **draft** (`definitionDraft.ts`): name, description and one row per key, every value held as text (a half-typed number is never lost). A row has a name, a type select and the fields of that type: number (default, min, max), boolean (default: not set, true or false), enum (options one per line, default picked from them), text, object (default as JSON) and collection (cap, item fields as `name:type` lines). Properties the form does not edit (unknown ones, an object key's `schema`) stay in the row's `rest` and are sent back untouched, because a save replaces the keys wholesale; unknown fields of the definition itself survive on the server. `definitionCompile.ts` is the only way from a draft to a request body and also produces the problems shown live under the name and under each row (empty, invalid, reserved or repeated names, non-numeric bounds, `min > max`, a default outside the bounds or not an option, repeated options, a bad cap or item field line, bad JSON), in plain language, by running the shared `stateDefinitionWriteSchema` over the rows that are fine so far. Save is off until the draft changed and nothing is wrong, and says why. A name another definition has (ignoring case) is shown inline as you type; the server's `409 STATE_DEFINITION_NAME_TAKEN` is shown the same way. **Renaming** a definition that chats hold state under is refused by the server (`409 STATE_DEFINITION_IN_USE`): the editor then shows a banner with the server's message and a link to each chat, makes the name read-only until the definition is opened afresh, and offers "Duplicate as '<name>'" (creates a new definition from the whole draft; the old one stays untouched) and "Keep the current name". The toolbar's "Duplicate…" asks for a name and copies the saved definition (it is off while the draft is dirty). Delete asks first; a definition still in use is explained in an error toast listing the chats and workflows. Edits made to the file on disk follow the usual live sync (`fileLiveSync.ts`): a clean draft reloads, a dirty one is never overwritten (a warning toast), and the editor's own save, announced before its response, is recognised through `classifyDraftChange` (`pages/draftChange.ts`, shared with the provider editor) instead of being reported as a conflict.

### Storage on the session

`session.state` is `{ turns: TurnEntry[] }` (additive: absent in older files, `[]` for new sessions; stored sessions are not parsed on read, so code reads entries through `readTurnEntries`, which skips anything malformed, and appends through `withTurnEntry`, which keeps unknown keys and entries it cannot read). The server appends one entry per **settled** turn inside `settleTurn`, in the same session update that saves the replies, whether the turn completed, failed or was stopped, and with or without writes:

```json
{
  "executionId": "6f1c…",
  "at": "2026-01-01T12:00:00.000Z",
  "completed": true,
  "replies": 1,
  "writes": [
    { "op": "set", "nodeId": "bump", "target": { "kind": "definition", "definitionId": "8d1f…", "key": "tension" }, "value": 6 },
    { "op": "add", "nodeId": "note", "target": { "kind": "definition", "definitionId": "8d1f…", "key": "injected" },
      "item": { "id": "6f1c…:note:1", "text": "a storm", "level": 2 } },
    { "op": "add", "nodeId": "pick", "target": { "kind": "node", "nodeId": "pick", "key": "draws" },
      "item": { "id": "6f1c…:pick:1", "text": "a storm", "entryKey": "c0ffee…:1a2b3c4d5e6f7a8b" } }
  ]
}
```

`replies` is how many assistant messages the turn saved (partial rows included) and `completed` means the run ended without an error or a stop. A turn whose workflow has after-reply sinks (see After Reply and post-turn runs) also carries `postExecutionId`, `postStatus` (`running`, `completed`, `error` or `stopped`) and, for an error, `postError` (cut to 500 characters; the whole text is in the post run's log). All three are additive and tolerant: a bad stored value drops the field, never the turn. `settleTurn` writes `postStatus: 'running'` in the same update that saves the replies, and when the post run ends `withPostRun` (`@st/shared`, the only way to append post writes) records the status and **appends the run's writes to the same entry, after the turn's own**, so deleting the turn's replies undoes them too and a later write to a key wins. Reply and post writes both count only while the turn does. The restart rule is computed on read: a stored `running` that the server does not hold (`TurnRegistry.hasPostRun`) is reported as an error, `The run was interrupted by a server restart.` (`effectivePostRun`), by `GET /api/sessions/:id/state` only (which decides which runs are live right when it reads the session and reads again, up to three times, before believing it: a run commits its result before the server lets go of it); the file is never rewritten for it and no startup pass runs. `target.kind: "node"` is a node's own implicit key (Draw's `draws`), which needs no definition; `nodeId` is always the writing node. Draw stores only the first 80 characters of an entry's text with each draw (a reminder for people; the `entryKey` fingerprint of the whole text is what is compared), so a long chat's state doesn't carry a copy of every drawn entry. **Scalars store the value after the write**: an `increment` is computed by the engine into a `set` (from the turn-start value plus the earlier writes of the same run, clamped), so nothing is ever replayed arithmetically. Collections store item-level `add` and `remove`; `delete` resets a key to its default (a collection to empty).

### The fold

The fold (`foldStoryState`, pure, in `@st/shared`, so server and web interpret state the same way) turns the stored entries and the messages into the current state. It never throws, never changes its input and never rewrites stored data. Its optional `turn` input reads the state as of that turn instead of the next one: the after-reply run of a turn reads at the turn's own number.

- **Presence.** A turn counts iff `entry.replies > 0` and at least one assistant message with its `executionId` still exists (not `streaming`; a `partial` row counts), or `entry.replies === 0` and `entry.completed`. User messages never count, so deleting only the user message of a turn undoes nothing, while deleting every reply of a turn undoes the turn. A turn with several replies counts until the last one is deleted. Entries missing for turns from before this feature are simply not counted.
- **Numbering.** The turns that count are numbered 1..n in stored order; the turn being run is n + 1 (`{{trigger.turn}}`, `ctx.state.turn`). Deleting a middle reply renumbers the later turns, and deleting the last reply makes its number free again.
- **Values.** A scalar key is the stored post-value of the most recent counting turn that wrote it (several writes in a turn: the last); `delete` makes it the default and still counts as a write. A collection is the items added by counting turns minus those removed by counting turns, newest first (later write first within a turn), cut to `cap` at read time: `meta.droppedByCap` says how many (items are never deleted from storage, so raising the cap brings them back). Writes made later do not change what earlier turns stored: deleting a middle turn keeps a later turn's post-value, deleting the last one rewinds to the one before it.
- **Validation against the current definition.** A stored value that doesn't fit (type changed, outside min and max, no longer an option) reads as the key's default, and produces a warning `{ definition, key, message }`; writes for a key the definition no longer has, or whose operation doesn't suit the key's type now (a `set` on what is a collection today), are ignored with a warning; the server adds `State "scene.tension": Stored value 11 is above max 10; using default 3.` to the run's `execution.warnings`. Writes for a definition that no longer exists are ignored silently. Restoring the definition brings the values back.
- **Meta per key**: `written`, `turnsSinceWrite` (turns since the last counting write; a key never written counts as written before turn 1, so it equals the current turn number), `writtenAtTurn` (`null` when never written) and, for collections, `count` and `droppedByCap`. Node implicit keys fold the same way (no definition, no cap, no validation).
- **History.** Per key, one point for each counting turn that wrote it (the newest 100, oldest first). A number, boolean or enum key's point is `{ turn, value }` (the value after that turn), a collection's `value` is how many items it kept, and a text or object key's point is only `{ turn }`, so a long chat's history stays small. A node's implicit scalar keeps only a number, boolean or `null`.
- Definitions are folded oldest first (`oldestFirst`), the order that decides which duplicate name wins.

### What a run sees and writes

The server folds the session at turn start (inside the `startTurn` mutation, with one listing of the definitions that also prepares the nodes' ports) and gives the engine a **snapshot**: the definitions, every key's value and meta (plus `itemTurns`, the turn that added each collection item), the nodes' implicit values and the turn number. `ctx.state` exposes it read-only (`values` for templates, `definition(id)`, `read(definitionId, key)`, `own(key)`; the methods hand out copies, and `values` is one frozen object shared by the run's nodes), and **reads never see the writes of the same run**: a value written this turn is visible to templates and State Read only from the next turn, and in the same turn only through a State Write node's output. `ctx.writeState(request)` only buffers. A node's requests count when the node **completes**: a node that errors or is cancelled contributes nothing, and calls after it returned are ignored. When the run ends the buffer resolves its requests in a fixed order (wave, then node id, then call order; never finish order) into stored writes: each `increment` is clamped and turned into a `set` from the running value, `add` items get the id `<executionId>:<nodeId>:<n>`, and a request for a missing definition or key is dropped with an execution warning. The result carries them as `writes` and so does `ExecutionFailure`: a failed or stopped turn keeps the writes of the nodes that completed before it ended (they count only if the turn left a reply or completed). Templates read only `state.values` (`{ <definition name>: { <key>: value } }`; `TemplateContext.state` needs just that property, which is why nodes can hand `ctx` to `renderTemplate`): keep state data nowhere else on the object a template receives.

### State Read and State Write

Both pick a definition and a key in their config (`definitionId`, `key`) and resolve their ports from the definition (`resolvePorts` with `resources.stateDefinitions`, snapshotted per run like presets). An unknown definition or key (also a State Write operation the key's type doesn't have) can't resolve its ports, so it is a validation issue in plain words naming the node (`WORKFLOW_INVALID` on the next turn), not a run-time error, and the editor keeps the node's edges meanwhile; a port that disappears (a collection's `count` after pointing at a number key) is pruned. A missing definition says `State definition <id> not found. Pick another state definition in the node's settings.` Server code builds `NodeResources` only through `nodeResources(context)`.

**State Read** (category State) has `read: 'value'` (default), `'meta'` or, for a collection key only, `'linked'` (`stateReadsFor` in shared; the panel only offers `linked` for collections and falls back to `value` when the key changes to another type):

| `read` | Outputs |
| --- | --- |
| `value` | `value`: `number`, `boolean`, `text` (enum and text), `object`, or `array` (collection, newest first). The turn-start value, the default when nothing was written. |
| `meta` | `written` (`boolean`), `turnsSinceWrite` (`number`), `writtenAtTurn` (`number`, optional: absent when never written), and for collections `count` (`number`). |
| `linked` | collections only: `value` (`array`), the items that link to chat messages and are still intact, in **chat order** (the same result as the `linked` template helper; a non-collection key is a validation issue). |

**Panels.** In the workflow editor State Read and State Write have custom node-ui panels (`panels/stateRead.tsx`, `panels/stateWrite.tsx`) instead of the generic form, so nobody has to paste a definition id. A shared picker (`StateKeyPicker`) offers the definitions from the editor's catalog (`NodePanelContext.stateDefinitions`, the whole records from `stateDefinitionsStore`) and, once one is chosen, its keys as `name (type)`; picking another definition keeps the key only when the new definition has it. An id or key that no longer exists stays visible as `Unknown definition (<id>)` / `Unknown key (<name>)`, and an "Edit definition ↗" link opens the definition in the editor in L while the workflow stays open in M (the link is the `/state-definitions?id=<id>` alias, opened in place by `PanelLink`). State Read adds a `Read` select (its value, or when it was written). State Write adds an `Operation` select that lists only what the key's type allows (`stateOpsFor`: `Set to a value`, `Add to the number`, `Add an item`, `Remove an item by id`, and `Reset to the default` or `Empty the list` for `delete`; one the key no longer allows stays visible as `Not allowed for this key`), then the **fixed value** editor for that key type and operation: a number box for a number key (an `Amount` box for `increment`, blank adds 1, with the key's bounds as a hint), a three-way select for a boolean (`No fixed value`, true, false), a select of the options for an enum, a text area for text, a JSON text area for an object (invalid JSON is flagged and reverts on blur), for `add` the item text plus one control per declared field, an item id box for `remove`, and nothing for a reset. Clearing a box removes the `value` setting from the config (it is never stored as empty text), and changing the key or the operation clears it, because it was typed for something else. A stored value the node would refuse (a text in a number key, an option the enum lost) is shown with the reason. The panel's help text explains that a connected value wins over the fixed one and the optional `when` input ("Run when"). The ports follow the config, so with a fixed value the `value` handle becomes optional. When definitions change, the editor resolves the ports of every State node again, so a key that changed type updates the node's handles without reopening the workflow. A node that is not set up yet (no definition or no key picked: any required text setting is blank, `unsetSettings` reads that off the node's config schema) cannot resolve its ports, which is no mistake: it raises no error toast, and the picker says what to pick next ("Select a state definition.", then "Select a key."). A real resolution failure of a node that is set up (its definition was deleted, the key is gone) still toasts once per node. Long definition and key names are cut inside the panel instead of widening it.

**State Write** (category State, a **sink**) always runs once its inputs are ready, whether or not a reply depends on it; with nothing connected (an unconnected `increment`) it runs every turn. **Gating:** every operation also has an optional `when` input (`any`, `requiredIfConnected`; its value is ignored). Connect a Condition branch or a Random chance output to it and the write only runs when that branch does (a branch not taken skips the node and writes nothing), whatever the operation needs as a payload: that is how a `delete` or a plain "add 1" runs only when something happened. Not connected, it runs every turn as before; switching the operation keeps the `when` connection. Its `op` depends on the key type:

| Key type | `op` | Input `value` | Output `value` |
| --- | --- | --- | --- |
| number | `set` | `number`, required; clamped to min and max | the stored value |
| number | `increment` | `number`, only when connected (the fixed `value` setting, else 1, when not; negative subtracts; a skipped source skips the node) | this turn's start value plus the amount, clamped |
| boolean, enum, text, object | `set` | typed `boolean`, `text`, `text`, `object`; an enum value must be one of its options | the stored value |
| any scalar | `delete` | none | the default |
| collection | `add` | `any`, required: text becomes `{ text }`; an object needs a string `text`; only the key's declared `fields` are kept (each checked against its type, undeclared fields and a client `id` dropped, missing ones omitted) | the stored item, with its id |
| collection | `add` + `messages` | the `add` row with the optional **`messages`** input (`any`, `requiredIfConnected`), which links the item to chat messages: see Message links | the stored item, with its `messages` link |
| collection | `remove` | `text`, required: the id of an item the key held at turn start; an unknown id stores nothing | the removed item (optional: absent when nothing was removed) |
| collection | `delete` | none | `[]` |

**Fixed value.** The optional config field `value` is a literal that stands in for the `value` input while that input is not connected, so the common writes need no helper node: set `scene.mood` to `"tense"`, `scene.tension` to `5`, increment by `2`, add a fixed item (`{ "text": "a storm", "level": 2 }`) or remove a fixed id. It is JSON in the workflow, so it keeps its type (`5`, `true`, `"tense"`, an object). A **connected input always wins**, and the fixed value is checked exactly like an input value (same plain errors, numbers clamped). `delete` ignores it. A missing or `null` setting is none: `set`, `add` and `remove` then need the input connected (it is `required`, a validation issue otherwise), while `increment` adds 1. With a fixed value the `value` input becomes optional (`requiredIfConnected`, as `increment`'s always is), and the ports re-resolve when it changes. The generic node form would only show `value` as a text box (text only), so State Write has its own panel (below) with a typed editor per key type.

A value of the wrong type or an enum option that doesn't exist is a node error naming the key (`scene.mood must be one of: calm, uneasy, tense, release; got "sad"`). The pass-through output of an `increment` is computed from the turn-start value plus this node's own amount; it differs from the stored value only when several nodes write the same key in one turn. Each node logs one line per write in the execution (`scene.tension: 3 -> 6`).

### Edits and deletes

Editing a message stamps `editedAt` and changes nothing else: the stored entries are never recomputed from content. Deleting a message is content-only; the fold recomputes which turns count, so deleting the last reply rewinds the state, a middle reply keeps later values and renumbers, and a user message changes nothing. Neither re-runs the workflow.

### Story state in the web

**The chat panel's Story state section** (`pages/chat/story/`) shows what the open chat has stored, read from `GET /api/sessions/:id/state`: the web never folds anything itself (the server's view is the truth; the one what-if fold, for the delete check, uses the shared `foldStoryState`). `useStoryState` makes ONE fetch per open chat and shares the result with the panel, the reply chips and the delete check. `startStoryLoader` (pure of React, tested with fake timers) loads it when the chat opens and reloads it, debounced to one fetch per 100 ms, after this chat's `sessions.changed` (a settled turn, a message edit or delete, a settings change; the connect snapshot has no id and counts too) and after `stateDefinitions.changed` (which waits 300 ms instead, because the server announces a saved definition twice: from the API write and from the file watcher); a change that arrives during a fetch causes exactly one more fetch and the older answer is dropped. As a safety net `Chat` also reloads when a running turn or message change finishes. Streamed tokens emit no event and cause no fetch, so a long answer costs one fetch at its end. A failed fetch keeps the last view and says so.

Per state definition that a present turn wrote (the others are one muted line, "Not used in this chat yet: …"), each key shows its current value, a sparkline for a number key written in at least two turns (an inline SVG built from the key's history by `sparklinePoints`, no chart library, with an `aria-label` listing the latest values), and either "never written" or "written at turn k", a link that scrolls the thread to that turn's LAST reply and flashes it (assistant messages carry `data-execution-id`, and so does the turn's user message, which is never the target; the panel closes after the jump when it covers the thread, in a narrow chat column, and `prefers-reduced-motion` turns the smooth scroll and the flash off). A turn that ran no Chat Output has no reply to go to: it reads as plain text, "written at turn k". A collection is a list, newest first, with its declared extra fields (`· level 2`), open when it has up to five items, and the note "N older items dropped by the cap" when the definition's cap cut some (shown even while the list is collapsed). A stored value that no longer fits its definition shows as a warning (the key reads as its default). The pencil next to a definition's name opens it in the definitions editor in L. **Node memory** (collapsed) lists what nodes keep under their own keys, such as Draw's recent draws, under the node's name (a node that was deleted from the workflow reads "A node that no longer exists"), newest first with "and N older" beyond the eight shown. Before anything is stored the section explains what story state is and offers "Open state definitions" (`LayoutActions.selectTab`, which shows the L list without changing the URL's other parts or an open wide editor). The state view has no key types, so a key's display kind is read off its value (`storyModel.ts`, pure). An object value is cut to one line, and its tooltip holds the full JSON. Only the chip marks a reply that was edited after its turn stored state; the panel does not. On touch screens the chip, the pencil and the turn link get the usual 36px target.

**The chip on a reply** (`story/TurnChip.tsx`, `turnChips.ts`, `describeWrite.ts`). A turn's chip joins the view's per-turn data to the chat's messages by `executionId` and belongs to the last non-streaming assistant message of that turn (a stopped reply counts), so a turn with several replies shows one chip and a turn whose replies are all gone shows none; only turns that still count (`turnNumber` not null) and wrote something get one. The card says `Turn 3 stored:` and lists each write, in write order and with current names: `scene.tension → 9`, `scene.mood → 'tense'`, `scene.tension reset to its default`, `scene.injected + 'a bell on a lost animal' (level 2)`, `scene.injected: removed 'a bell…'` (the text comes from the add in the same view, else "an item"), `Draw #1 (draw): drew 'resin smell'` (other node keys read `<node>: remembered 'x' (<key>)`); text is cut at 60 characters, a deleted definition reads `(deleted definition).key` and a deleted node "A removed node". If any reply of the turn was edited (`editedAt`) the card adds "Edited after it was stored: the values above came from the original text", because an edit never changes stored state. The lines are described once per loaded view (`describeTurns`); placing the chips is one pass over the messages per render (`chipsFor`), so a streamed token costs no more than before.

**Deleting a reply that undoes state** (`story/undoList.ts`). The trash button asks `undoneByDelete` (only on the click, never while rendering) whether deleting the reply would change the story state. It only does when the message is an assistant reply of a turn that still counts and wrote something, **no other reply of that turn survives** (then the turn still counts and nothing is undone), and a value would actually change. The answer comes from the shared `foldStoryState`, run twice over the chat's messages, with and without the reply, with the turn entries rebuilt from the state view and the definitions from `stateDefinitionsStore`; the lines compare the folded values of the keys the turn wrote, so a value that a later turn overwrote is not listed and a set to the same value is not either. Each line names the key and where it goes back to: `scene.tension (back to 4)`, `(back to the default, 3)` when it had never been written, `(back to 'calm')` for an enum or text (cut at 40 characters, `back to empty text`), `(restored to its earlier value)` for an object (its content is never shown), `scene.injected (forgets 'a bell…'; brings back 'x')` for a collection (three items at most, then `and N more`; a removal that is undone brings its item back, and a cap that was hiding an older item brings it back) and `Draw #1 (draw) forgets 'resin smell'` for node memory. When there is at least one line the trash button goes straight to `window.confirm` ("Deleting this reply also undoes what its turn stored: …"), one confirmation instead of the inline check-mark step; any other delete keeps the inline step. The click itself is `deleteClick` (`story/deleteConfirm.ts`: no lines is the inline step, lines ask with `window.confirm` and a cancelled dialog keeps the reply). Limits: the state view cuts very long write values (`truncated`, the shared `previewWrite`), so a long text shows its cut text and an object that long never shows its value; when such a cut makes two different values look alike to the fold (two long objects both read as the default) and the reply is the last to write the key, the key is listed as `scene.flags (may change)` instead of being left out; and when the view has not caught up with the chat yet (the turn is missing from it) the check finds nothing and the ordinary inline step applies. The server's fold decides what actually happens either way, and the panel and chips reload when the delete is announced.

**After-reply runs in the chat** (`story/postRuns.ts`, `postRunText.ts`, `PostRunStatus.tsx`, `PostFailures.tsx`, `usePostRunAlerts.ts`). The same shared view tells the chat about the post run of each turn (`postStatus`, `postExecutionId`, `postError`), so nothing polls and nothing is fetched for it: the post run's settle publishes `sessions.changed`, which already reloads the view. While the newest running one exists a quiet row above the composer says `Running after-reply steps… (turn 3)` with a spinner and a Stop button (an `IconButton`, which calls the chat's one stop: it ends whichever job runs, then reads the state again, so a row left stale by a server that was killed and restarted clears once the server answers); the composer is not locked, because the reply is complete. The thread watches its own viewport as well as its content, so the row appearing never clips the newest reply. A failed run toasts **once**: the first view loaded for an open chat is a baseline (failures already in it, such as one a restart cut short, only show on the chip), and every later view's failed run that was not seen yet toasts `After-reply steps failed on turn 3: <message>` and is remembered (`nextAlerts`; never a running-to-error transition, because a fast failure can be missed between two views). A stopped run never toasts. The turn's chip also appears for an ended run that stored nothing (an alert icon marks a failure); its card shows the error, or that the steps were stopped or stored nothing, and an `After-reply run details` disclosure with the run's log for every ended run, completed ones included (`ExecutionDetails` with `optional`: its fetch is silent, so a run with no log, as after a restart, says `No log was saved for this run.` instead of toasting a 404). Failures also stay visible in the chat panel's Story state section, which lists the newest three failed or interrupted runs (`Turn 3`, `Turn 3 (no reply)`, or `A turn whose replies were deleted`, the error and the same log disclosure): a turn without a reply has no chip, and a failure that happened while the chat was closed never toasts. A message sent while a run works shows `Waiting for the after-reply steps to finish` in place of `Preparing a reply` until its turn starts, and the composer's button then reads `Cancel queued message` (Esc too): it aborts that message's request (the server drops it unstored, the text returns to the composer) and leaves the post run to the row's Stop. All wording is in `postRunText.ts`.

`GET /api/sessions` leaves `state` out of the summaries; `GET /api/sessions/:id` returns it. `stateDefinitions.changed` (`invalidFiles`) is published by the `data/state/definitions/` watcher and after every API write, like the other YAML resources (see Live reload). The preset preview renders the chat's next-turn state and `trigger.turn` when given a session, and every key at its default at turn 1 without one.

## Ports & types

Ports declare `text`, `number`, `boolean`, `object`, `array`, `messages`, `character`, or `any` (legacy ports default to `any`). The same compatibility rule is used in the editor and executor:

| Output → input | Result |
| --- | --- |
| Same type, or `any` on either side | Pass through unchanged |
| `number`, `boolean`, `object`, `array` → `text` | Convert to text (objects/arrays as pretty JSON) |
| `messages` → `text` | Convert to a `role: content` transcript |
| `messages` → `array` | Pass through unchanged |
| `character` → `object` | Pass through unchanged (a character is an object) |
| `character` → `text` | Rejected; no implicit character serialization |
| All other differing types, including `text` → `number`/`boolean` | Rejected; no implicit parsing |

To turn text into a number, boolean, object or array, use a **Parse JSON** node: the conversion is explicit and fails loudly instead of guessing.

Memory's `history` output is `any` because its `format` setting can emit either text or messages. Hover over a port to see its type and description; compatible connections that convert data are dashed. Invalid saved edges remain visible in red for correction.

## Data and secrets

`data/` is gitignored and holds user data that must be preserved across upgrades: workflows, sessions, execution logs, characters, personas and avatars live as separate JSON files written via temporary-file-and-rename; presets, providers, collections and state definitions are YAML files (see Preset files below, Providers, Authored collections and Story state above). A chat's story state is the additive `state` field of its session file (absent in older files). Never reset or delete `data/`. Persistence is behind a `Repository<T>` interface for a future database.

Schema changes stay additive and backward compatible: stored records keep unknown fields (zod `passthrough`), new optional fields use `.default()`/`.optional()` so old files still parse, and writes migrate-on-write (normalize with `safeParse` + defaults, keep unknown fields, no destructive rewrites). If a breaking change is unavoidable, ship an explicit migration script plus a backup step. Seeds only create missing records and never overwrite user-modified ones. Corrupt JSON files are never auto-deleted: `list()` skips them with a warning, `get()` throws with the file path.

### Preset files (YAML)

Presets (and providers and collections, see Providers and Authored collections) are the record types stored as YAML instead of JSON: `data/presets/<slug-of-name>.yaml`, handled by `PresetRepository` (`storage/preset-repository.ts`; format in `preset-yaml.ts`). The directory scan, stamping, locking, atomic writes and file naming are shared with providers and collections through the generic `YamlRepository<T>` (`storage/yaml-repository.ts`, parameterized by a `YamlCodec`; names in `yaml-filenames.ts`). The HTTP API and contract are unchanged.

```yaml
name: My roleplay preset
description: Optional
inputs:
  - key: history
    dataType: messages
  - key: message
    dataType: text
entries:
  - displayName: Main prompt   # the editor label
    kind: message
    role: system
    enabled: true
    content: |
      Write a natural, in-character reply.
      {{character.system_prompt}}
  - displayName: Author note
    name: "{{char}}"           # optional message name sent to the model (a template)
    kind: message
    role: system
    enabled: true
    placement:        # depth placement: points at a slot id
      mode: depth
      entryId: chat-history
      depth: 1
    content: "{{character.personality}}"
  - id: chat-history  # slots targeted by a depth placement carry a readable id
    displayName: Chat history
    kind: slot
    inputKey: history
id: 5d6c72c7-5185-4963-8227-527f12ef9eea   # bookkeeping last
createdAt: 2026-01-01T00:00:00.000Z
updatedAt: 2026-01-01T00:00:00.000Z
```

- **Identity** is the `id` inside the file, never the file name, so files can be renamed or edited by hand. Nothing is cached: every operation re-reads the directory.
- **File names** are the slugified preset name (letters and digits of any script, lowercase, hyphens, at most 80 characters; reserved Windows names such as `con` get a `-preset` suffix; an empty slug becomes `preset`). A collision (compared case-insensitively) adds `-2`, `-3`, ... Renaming a preset writes the new file, then removes the old one. A file whose preset name did not change keeps its name, even if you renamed it by hand. `.yml` is read too; files are always written as `.yaml`.
- **Optional keys:** `id` on inputs and entries, `enabled` (defaults to `true`), `placement` (defaults to ordered), `inputs`/`entries` (default empty). Items without an `id` get `input-<n>`/`entry-<n>` from their position (1-based); this is deterministic but shifts if you reorder them by hand. Machine ids (UUIDs) are not written: they are replaced by these derived ids on the next save, and slots targeted by depth placements get a label derived from their `displayName`.
- **Legacy entries:** files written before entries had a `displayName` used `name` as the label. An entry with `name` and no `displayName` is read as `displayName` with no message name (`upgradeLegacyPreset` in `@st/shared`, applied to raw data before validation by the YAML loader and the JSON migration). The file is not rewritten on read; it gets the new shape on its next save. Entry keys are written in the order `id, displayName, name, kind, …`.
- **Content** is lossless: multi-line strings are literal block scalars. Content that block scalars cannot carry (for example lines made only of whitespace, or CR characters) is written double-quoted instead. Unknown fields are preserved at every level.
- **A new hand-written file** with no `id` is valid: the server stamps a fresh `id` (and `createdAt`/`updatedAt` if missing) into the file once, appending after your content, then treats it as a normal preset.
- **Invalid files** (bad YAML, fail the preset schema) are skipped with a warning naming the file and the reason, and are never modified or deleted. If two files declare the same `id`, the first by file name wins and the other is skipped with a warning.
- **Delete** removes only the preset's YAML file.
- **Migration:** at startup, before seeding, each `data/presets/<id>.json` that parses as a valid preset is written as YAML, read back and compared with the original (only machine ids may differ), and then renamed to `<id>.json.migrated`. The JSON content is never changed or deleted, and the `.json` filter ignores it afterwards. A failed verification removes the new YAML and leaves the JSON in place with a warning; unreadable or invalid JSON is left untouched with a warning; if a YAML with the same id already exists the JSON is just renamed. Running it again does nothing. To roll back, delete the YAML and rename `.json.migrated` back to `.json` (an older server then reads it).
- Edits made on disk are picked up by the next API call, and the open web app updates live (see Live reload below).

#### Live reload

The server watches `data/presets/`, `data/providers/`, `data/collections/` and `data/state/definitions/` (`watchResourceFiles` in `services/change-events.ts`; `fs.watch`, non-recursive; temp files of our own atomic writes, editor swap/lock files such as `.x.yaml.swp` or `.#x.yaml`, and non-YAML files are ignored). Bursts, including editors that save through temp file + rename, are debounced into one notification, followed by a rescan. The watcher is only started by the server entry point (`createApp(dir, { watch: true })`), re-arms itself after errors, and is closed with the app. It watches the directory by its resolved long path, because libuv aborts the whole process when Windows reports long names for a directory given by its 8.3 short name.

| Method and path | Purpose |
| --- | --- |
| `GET /api/events` | Server-Sent Events (`changeEventSchema`, event name = `type`). `presets.changed`, `providers.changed`, `collections.changed` and `stateDefinitions.changed` with `invalidFiles: { file, reason }[]` (empty when every file loads), plus `workflows.changed`, `characters.changed`, `personas.changed` and `sessions.changed`, each with an optional `id` of the affected record. |

The server sends the current state right after a client connects, so a client that reconnected resyncs, plus a `: keepalive` comment every 15 seconds. Events only say that something changed; clients re-fetch. Writes made through the API trigger the event too, which is harmless.

Record events are emitted by the repositories themselves: `workflows`, `characters`, `personas` and `sessions` in the context are `NotifyingRepository` wrappers (`services/change-events.ts`) that publish `<resource>.changed` with the record id after every successful `save`, `update` and `delete` (avatars, card import and message edit/delete included), so a new write path cannot forget it. The connect snapshot sends each of these without an `id`. Presets, providers, collections and state definitions are not wrapped: the file watcher covers them, and provider, collection and state definition API writes publish through `publishFileChange` as well. A chat turn writes through the wrapper's `silent` repository (streamed rows and flushes would otherwise fire per token) and publishes one `sessions.changed` when the turn settles, whether it completed, failed or was stopped. Tests that spy on a repository's internals must spy on `.silent`.

In the web app, one shared `EventSource` (`api/events.ts`) serves every listener. On `presets.changed`, the Presets page:
- refreshes the list, and leaves the list and editor untouched when the data is identical (a UI save followed by its own event is a no-op);
- reloads the open preset when its editor has no unsaved changes, keeping the selected entry by **position** (entry ids are re-derived on every read); if the preset no longer exists, closes the editor with an info toast;
- never touches a dirty draft: it shows one warning that the file changed on disk. Saving that draft **overwrites the disk edits (last write wins)**; if the file was deleted, saving fails with `NOT_FOUND`, so duplicate the preset to keep the edits;
- shows one persistent warning per invalid file, with the file name and the reason (bad YAML, schema errors, duplicate ids). It is shown once per (file, reason) and dismissed when the file is fixed or removed. Invalid files are skipped, never modified.

The Presets page's list and live sync share the presets store: the sync calls `presetsStore.refresh()` (joining the store's own event-driven fetch, so there is one request per change), then decides what the fresh list means for the open editor. The workflow editor's preset catalog (LLM node ports) is the same store. A workflow whose LLM node points at a preset that was deleted or broken on disk is not guarded by `PRESET_IN_USE`; running it fails with `400 WORKFLOW_INVALID` whose issue names the node and the missing preset id.

Back up the whole `data/` directory (at minimum `secrets.enc.json`, `.master.key`, the JSON files and the preset, provider and collection YAML files). Stop the server first, then copy the directory to a timestamped zip. `data/` stays gitignored.

Secrets are AES-256-GCM encrypted in `data/secrets.enc.json`; a 32-byte key comes from `SECRETS_KEY` (64 hex characters), or is generated in `data/.master.key` on first start. **Back up both encrypted secrets and the master key.** The secrets API returns only names and masked hints; key values can only be set or deleted. For a production deployment, provide `SECRETS_KEY`, restrict access to the server and data directory, and put authentication in front of the API.

Secret `set` and `delete` operations serialize their entire encrypted-file read/modify/atomic-write sequence through one store-wide lock, shared across secret names. The reusable `storage/lock.ts` keyed lock also backs repository mutations. Locks are in-process and scoped to their owning store/repository instance; they do not coordinate multiple server processes writing the same directory.

Workflow and preset PUT replacements use `repository.update`, sharing the per-record lock with DELETE. PUT preserves the stored id/creation time and returns the standard `404 NOT_FOUND` envelope if the record is absent, including when DELETE wins a race; it never creates or resurrects records. Plain `save` creates new records (character/persona imports generate new UUIDs); chat's intermediate save is already inside its session update lock. Do not nest `update`/`delete` for the same key.

Executions report node status, timing, outputs, errors, the LLM wire exchange (`wire`; older logs have the canonical `request` instead), a `warnings` list (older logs default to an empty list), the run's random `seed` and the resolved chat `settings` it used (both absent in older logs). The log of an after-reply run has `part: 'post'`, `turnExecutionId` (the reply run's log) and only the post part's nodes; a reply log has neither field. A node's `logs` holds the lines it wrote with `ctx.log` (absent when it logged nothing), such as Parse JSON's raw input on failure. Every run gets a seed (`executeWorkflow`'s `seed` option, otherwise a random UUID); each node's `ctx.random()` draws from a deterministic stream seeded by `${seed}:${nodeId}` (cyrb128 hash, sfc32 generator, `packages/engine/src/seeded-random.ts`), so the same seed reproduces every roll of a run. Nodes in a failed execution wave are aborted and allowed to settle **only until their original node deadline** before the failure is returned (`definition.timeoutMs`, otherwise `nodeTimeoutMs`, otherwise 30 seconds). An abort-ignoring sibling that has not settled by its deadline is still recorded as `cancelled`, distinct from an unselected condition branch (`skipped`). Its detached work may continue; the engine does not claim to have stopped it, but ignores its results, wire-recording callbacks and events. Completed Chat Output replies are retained even if another node later fails; cancelled and skipped outputs produce no messages. After cancellation cleanup returns, logs and replies no longer change. Per-node setup errors are recorded as execution failures rather than silently discarded wave rejections. A required output port with outgoing edges must be returned by its node; an output declared `optional` may be omitted (Condition's mutually exclusive branch outputs are optional). An input declared `required` must be connected and skips its node when its source was skipped; an input declared `requiredIfConnected` may stay unconnected, but once connected it skips its node the same way (Random chance's inputs). Otherwise a node whose connections are all inactive (skipped sources, ports not produced) is skipped; an input declared `neverSkips` never counts towards that, so a node whose only connection is such an input still runs without it (Recall's extra `text`).

Engine events feed the streaming transport (`TurnStream` on the server) and are also available to other observers. The `onEvent` observer is a best-effort synchronous notification: exceptions from it are swallowed and never change workflow success/failure, kept replies, execution details or cancellation cleanup, including for the terminal `execution:complete` event. Message requests for one session are serialized through all completed replies or failure, so each prompt sees the prior exchange; different sessions can still execute concurrently. Workflow edits affect subsequent messages in all sessions bound to that workflow.
