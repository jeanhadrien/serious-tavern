# AGENTS.md — notes for AI agents working on this repo

Read `PLAN.md` for the vision and `README.md` for usage and architecture before making changes.
For web layout work, `docs/FRONTEND-LAYOUT.md` is the agreed design reference; for interaction behaviour (Escape, shortcuts, unsaved work, confirmations, drag and drop, resizing), `docs/FRONTEND-UX.md`.

## What this is
A chatbot web app. Each chat reply comes from a user-built workflow of nodes, edited visually in an n8n-style editor. The frontend is a **thin client**: all storage, secrets and workflow execution live in the backend.

## Workflow conventions
- **Orchestration:** the main assistant acts as the orchestrator. It delegates substantial coding to a coding sub-agent (gpt-6-sol), then **verifies the work itself** before reporting back.
- **Coding agents are not persistent.** Spawn a **fresh agent per task**; don't rely on or reuse an agent's memory from earlier tasks.
  - Each brief must be self-contained. Tell the agent to read `AGENTS.md`, `README.md` and `PLAN.md` first, and include the task spec, relevant file paths, constraints, verification commands and commit rules.
  - Any knowledge worth keeping goes into the repo (this file, README, code comments/tests), not into an agent's context.
  - After a task, the orchestrator updates this file with any new conventions, contracts or gotchas the agent discovered.
- **PLAN.md is owned by the orchestrator/user.** Coding agents must not modify or delete it; they update `README.md` for technical docs.
- **Commits:** commit each feature separately. Include the trailer `Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>`. Commit any pending changes before starting new work.
- **Scope:** keep it modular and simple. 

## Layout (npm workspaces, TypeScript strict, ESM, packages consumed as TS source)
- `packages/shared`: zod schemas and types (workflow, ports, `canConnect` compatibility and coercion rules). This is the single source of truth for both front and back.
- `packages/engine`: graph validation, wave-based parallel executor, templating (Handlebars runtime over the turn context: `{{input.x}}`, `{{trigger.message}}`, `{{history}}`, `{{#if}}`/`{{#each}}` blocks, `(eq …)` comparisons, no code eval). Node types live in `src/nodes/<type>/index.ts` and are registered in `registry.ts`.
  - `prepareWorkflow` (in `prepare.ts`) parses configs, resolves ports and snapshots resources **once**. `validateWorkflow` wraps it, and `executeWorkflow` accepts its result. Prepare again for each turn, and load node resources through the resolvers.
  - Execution failures carry `nodeId`/`nodeType` as data. Never parse error messages.
  - Validation returns structured `ValidationIssue`s (`{ message, edgeId?, nodeIds? }`), not bare strings. Messages are plain language and name nodes via `nodeDisplayName` (`Label #k (type)`); ids travel only in `edgeId`/`nodeIds`, never in the text. The `WORKFLOW_INVALID` error details are `{ workflowId, workflowName, issues }` (see `workflowInvalidDetailsSchema`); the web transport links the toast to the workflow and highlights the offending edge.
- `packages/node-ui`: config forms generated from JSON Schema, custom panels (`src/panels/`), template-variable hints.
  - Panels get catalogs (presets, characters, providers, collections, state definitions as whole records, the open workflow's chat `settings`) and `renderLink` through a typed `context` prop. node-ui never imports react-router or the web API clients.
  - **State panels** (`panels/stateRead.tsx`, `panels/stateWrite.tsx`, the shared `StateKeyPicker`; pure logic in `panels/stateConfig.ts` and `panels/stateValue.ts`): the operations a key allows always come from `stateOpsFor`, never a hand-written list. `retarget`/`pickDefinition`/`pickKey` are the only way the panels change `definitionId`/`key`: they fit `op` to the key type and (State Write) drop the fixed `value` when the target changes. Unknown ids stay visible as `Unknown definition (id)`/`Unknown key (name)`. The "Edit definition ↗" link is the `/state-definitions?id=` alias (`layout/routes.ts`, `stateDefinitionLinkId`), which `PanelLink` opens in L in place. The editor re-resolves dynamic ports when the definitions list changes (`useDynamicPorts` deps). `pickOp` is the only way the panel changes `op` (it drops the fixed value), `pickerHint` says what to pick next, and the rules both sides check (read modes `stateReads`, an item's fit `collectionItem`/`itemFieldNeeds`) live in shared (`state/node-values.ts`) for the engine and the panels alike, never copied; `parseDecimal` there is the UI-side rule for typed number boxes (the panels and the definitions editor; the engine never parses text into numbers).
  - Array fields in any shape other than `{key,value}[]` are shown as read-only JSON.
  - The generic form shows a field's zod `.describe()` text as a hint, and a cleared number field **without a schema default** is stored as unset (`undefined`, `numberFieldValue` in `fields.ts`), so optional numbers can fall back to a node's own default (Random's per-mode bounds). A field with a default keeps storing `0` when cleared: storing unset there would redisplay the default mid-edit (typing after clearing `10` gave `105`).
- **API contract:** `packages/shared/src/api/` holds zod schemas and types for the request and response of every endpoint. It is the only definition of the API.
  - To add or change an endpoint, update the contract first. The server parses its input with the contract and types its response from it; the web client uses the same types.
  - Server tests check that responses match the contract schemas.
  - Don't declare request or response types locally, and don't put inline `z.object` schemas in routes.
- `apps/server`: Fastify 5 on port 3001 (run with `tsx`). JSON-file storage under `data/` (gitignored, atomic writes). AES-256-GCM secrets.
  - `app.ts` only wires things together.
  - `context.ts` sets up the repositories and secrets; `errors.ts` has HttpError and the error handler.
  - `routes/<resource>.ts` holds thin handlers; the logic lives in `services/`: `chat.ts` (runs a message under the session lock), `turn-start.ts` (prepares the reply list and splits it into sections), `reply-section.ts`/`reply-run.ts` (the streamed runs), `after-section.ts` (the workflows that run after the reply), card import/export, preset preview.
- `apps/web`: React 19 + Vite on port 5173, proxying `/api` to the server.
  - `api/`: typed clients per resource, built on `transport.ts` (ApiError, toasts, `{silent:true}`). Pages call these clients, never raw paths.
  - `alerts/`: toast store and `<Toaster/>`.
  - `connection.ts`: `isValidConnection`.
  - `stores/`: shared list stores (`createListStore`, read with `useList`) for workflows, presets, characters, personas and sessions. They re-fetch on their change event. Pages read lists from them and never keep their own copies. After a local write, call `store.refresh()` to read your own write. Drafts and the open chat session stay local state that a list refresh never touches.
  - `layout/`: the three-column shell (design in `docs/FRONTEND-LAYOUT.md`).
    - `state.ts` is a pure reducer: slot rules, wide vs narrow editors, compact mode, phone mode (compact mode shown one column at a time: `mobile`, `pane`), dirty flags. `derive.ts` maps it to view placements and header icons. Change rules there, with tests, never in components.
    - `Shell.tsx` mounts **every view exactly once, in the fixed `VIEW_KEYS` order**. Moving a view only changes its `grid-area`, and hiding it sets `hidden`, so nothing remounts (streams, drafts, canvases survive). Never render a view conditionally or in a different position.
    - `useChat` lives in the shell, so it re-renders on every streamed token. Views that take no props are module-level constants (`STATIC_VIEWS`, with `DIRTY_SOURCES`, in `layout/staticViews.tsx`) so React skips them. Keep new views stable the same way, or memoize them.
    - **The composer draft is per chat in `localStorage` (`pages/chat/composerDraft.ts`, key `st.composer.<sessionId>`), never in the token path.** Only typing writes it (`useChat.setContent`, stable identity, debounced by `createDraftSaver`, which carries the chat id with the pending text); `enter` (open, create, close) flushes the previous chat's draft and loads the new one, `pagehide`/unmount flush, `send` removes the stored draft before the request and only a cancelled queued message is put back. Copy (`copyText.ts`) copies the stored `content`, never `reasoning`.
    - The chat's side panel (`ChatPanel`, per-chat sections: Settings and Story state; its header toggle is "Chat panel") is local state of the chat view, not a layout view: it never touches `layout/state.ts`. It is memoized and its props keep their identity across streamed tokens. Settings saves go through `useChat.updateSettings`, which merges only `settings` from the PATCH response into the open session (never its messages, `withStoredSettings` in `pages/chat/openSession.ts`) and is not gated by a running turn. The panel's saver keeps one PATCH in flight, so answers arrive in order; header metadata patches keep the local `settings` (`withStoredMetadata`).
    - Providers and state definitions (`list:providers`/`editor:providers`, `list:stateDefinitions`/`editor:stateDefinitions`) are narrow editors with their list in **L**; characters, personas and collections have theirs in R.
    - A resource's list (a side column) and its editor (M or its own column) are separate views that share an **editor store** (`stores/editorStore.ts`). The store holds the open id and dirty flag, plus the list's `open`/`discard` requests, which the editor applies through `useEditorCommands`. `open` of another item names it as `currentId` at once (clean): the editor applies the request in an effect, and without this the render in between wrote the previous item into the URL (a stray history step). An editor's `open` handler must therefore always load the item. **Unsaved-work guard:** `open` itself never asks; the callers do. Every path that replaces the open item (a list click, create, duplicate, import, a link) does `if (!(await store.confirmSwitch(id))) return;` first (`confirmSwitch()` with no id for create/import), **before any server write or layout change**, so Cancel leaves the draft, URL and layout untouched. Each editor registers `{ label, save }` with `useEditorSaver(store, …)` (its `save` resolves `Promise<boolean>`: true only when saved; a failed save already toasted) so the dialog can offer Save. Back/Forward (`fromHistory`) never asks, because it never discards. `Shell` also warns on tab close or reload while any editor is dirty (`useUnsavedWarning`, `beforeunload`). The draft itself stays inside the always-mounted editor. Views reach layout actions through `LayoutActions` context, and dirty flags reach the header dots via `useDirtySync`.
    - **The layout lives in the URL** (`/?session=…&left=…&wide=preset:<id>&right=character:<id>`, defaults omitted). A narrow editor open in L is `left=<name>:<id>` (`provider:<id>` and `stateDefinition:<id>`); `LayoutTarget.leftEditorOpen` and `LayoutUrl.leftId` are the L twins of the R fields, and `sameContent` compares both. The pure (de)serializers are in `layout/url.ts`, and `useLayoutUrl` syncs both directions. Content changes `push`; tab switches and corrections `replace`. Build in-app links with `layoutHref`. Legacy paths (`/presets?id=…`, `/workflows?workflow=…&edge=…`, `/characters`, `/collections?id=…`, …) stay as inbound aliases in `layout/routes.ts`, because node-ui's "Edit preset", "Edit collection" and "Edit definition" links emit them. In the workflow editor, `PanelLink` opens a collection link in R and a state definition link in L in place (`panelLinkTarget`; a restored alias URL would close the workflow). History navigation never discards a dirty draft or switches a streaming chat.
    - Live checks in the built-in browser pane: when the app window isn't in front, the pane has a 0px viewport, never paints, and ResizeObservers don't fire. Force a size with `resize_window`, and don't trust React Flow measurements or screenshots there.
  - `pages/<area>/`: components and hooks per page (chat, workflows, entities, presets). Keep files focused, roughly under 250 lines. Page components take explicit, minimal props interfaces (not a whole hook result); the page file is a thin composition.
  - `components/`: shared UI pieces (e.g. `IconButton`). Page-specific styles live next to the page (e.g. `pages/chat/chat.css`), not in `style.css`.
  - **Reordering:** a list reorders only through `components/sortable/SortableList` (never import dnd-kit anywhere else), keeps its up/down buttons (from the row's `moveUp`/`moveDown`) and needs ids that are stable for the life of the draft: `getId(item, index)` returns the item's own id, or one from `useRowIds` for items that have none (kept beside the list, never in the draft, so never sent and never dirty). `Alt+↑/↓` on a focused row is handled in the row (`keyMove`, not in `keyboard/`); the pure move is `moveItem`. A row's `renderItem`/`label` should be `useCallback`ed so unchanged rows skip rendering (collection entries). Read-only lists pass `disabled` (no handles). node-ui's collection picker cannot import from the web app: up/down buttons and `Alt+↑/↓` only, no drag.
    - **Resizing** (`components/splitter/`, design in `docs/FRONTEND-UX.md`): every resizable divider is the one `Splitter` (pointer drag, plain arrows by `step`, double-click `onReset`; it owns no size). A remembered size is `useStoredSize(key, { initial, min, max })` (`st.size.<key>` in `localStorage`, guarded: `safeStorage`; only the user's own value is stored, `initial` is the default until then and after `reset`). The shell's column handles are `ResizeHandle` over it (widths in `layout/widths.ts`, `resetSide` on double-click). In-page splits: chat panel width (`chat-panel`, in `ChatPanel`'s own state, never a prop), workflow node/settings panel (`workflow-panel`, one shared stored width), preset entry list (`preset-list`). A stored size reaches CSS as a custom property (`--chat-panel-width`, `--config-panel-width`, `--preset-list-width`) that only the side-by-side rules read; the stacked and overlay container queries ignore it and hide the splitter (`display: none`). New splits do the same; never add a splitter to a stacked or overlay layout.
    - **Dialogs** (`components/dialog/`): every question goes through `dialogs.ask({ title, body, actions, cancelLabel })` (resolves with an action id or `CANCEL`) or `confirmDelete(title, body?)`, shown by the one `<DialogHost/>` in `main.tsx` (native modal `<dialog>`, Cancel focused first, Escape and the backdrop cancel, questions queue). Never call `window.confirm`. When to ask is in `docs/FRONTEND-UX.md` (Confirmations): deleting something stored asks, edits inside a draft don't.
    - **Keyboard** (`apps/web/src/keyboard/`; behaviour in `docs/FRONTEND-UX.md`): `useKeyboard` (called once in `Shell`) is the app's one `document` keydown listener; never add another in a component. Escape does one thing, chosen by the pure `escapeStep` (a field that acted, then an open `<dialog>` which handles itself, then the newest layer, then leaving a field, then the area). Popovers and cards register with `useEscapeLayer(open, close)`; a layout view's Escape is `useEscapeArea(viewKey, handler, fallback?)` (handlers newest first, the first to return true wins; `fallback: true` runs after all others, which is how `useDefaultEscapeAreas` in `layout/useEscapeAreas.ts` gives every editor view its "close the editor" default under the pages' inner handlers). The area is the focused element's `section.view[data-view]` (after a click on a non-focusable part, the last pointer press's view); a hidden view never has it. A field that acts on Escape calls `event.preventDefault()`, and only when it acts (composer while busy, message editor, model picker with its list open). Chat Escape stops a reply only when `chat.busy`, which is false while only workflows after the reply run. `Ctrl/Cmd+S` always suppresses the browser's save and calls `editorStore.save()` (the registered saver, only for an open dirty draft) of the focused `editor:<resource>` view (`ITEM_SOURCES` in `layout/itemSources.ts`). Shortcuts are declared in `SHORTCUTS` (`keyboard/shortcuts.ts`) with the pure `matchShortcut`. **Area shortcuts** (`Mod+Z` undo, `Mod+Shift+Z`/`Mod+Y` redo; type `AreaShortcut`) go to the view with the keyboard through `useShortcutArea(viewKey, { undo, redo })` (`keyboard/shortcutAreas.ts`, same registry pattern as `useEscapeArea`: handlers newest first, a handler returns true when it acted and `useKeyboard` then calls `preventDefault`); `areaShortcutAllowed` keeps them out of fields (the browser's text undo works there), open dialogs and keys a field already handled. The native `copy`/`paste` events are the same registry (`ClipboardShortcut`, handlers get the `ClipboardEvent`, `runClipboard`), not keys. A new area shortcut is a `matchShortcut` result, an `AreaShortcut` member, a `SHORTCUTS` entry and handler names in `useShortcutArea`.
    - **Editors** (`components/EditorHeader.tsx`, `pages/useDraft.ts`; design in `docs/FRONTEND-UX.md`): every editor renders `EditorHeader` (back for narrow editors, the title or a name input, the marker text `Unsaved changes` in a `.dirty-dot` span, `extra` buttons, then Save, Revert, Duplicate, Delete in that fixed order; an action left out isn't rendered, Revert only shows while dirty and asks nothing). Never write a per-page toolbar. Characters, personas and presets keep their draft in `useDraft` (draft + saved snapshot, `load`/`set`/`revert`/`clear`, reports to the editor store; pure part in `draftState.ts`); it does not apply store commands or register the saver, the editor does (`useEditorCommands`, `useEditorSaver`). Providers, collections, state definitions and workflows use the header only because their drafts are not a plain copy of the saved item (text forms, async load, the canvas). Their Revert: providers and state definitions rebuild the draft from the saved record (a refused rename stays locked), collections re-read from disk, workflows reload the last loaded or saved workflow through `load`.
  - Icons: `lucide-react` only. Icon-only buttons need `aria-label` and `title`.
  - Markdown: `react-markdown` + `remark-gfm` with `skipHtml`. Never render raw HTML from message content (no `rehype-raw`).
  - Message edit/delete (`PATCH`/`DELETE /api/sessions/:id/messages/:messageId`) change stored content only and never re-run the workflow. An edit also stamps `editedAt`; a delete is content-only, but the story state fold then recomputes which turns count.

## Key contracts (don't break)
- **API errors:** always `{ error: { code, message, details? } }`, via the global Fastify error handler. No stack traces in responses.
- **Web client:** non-2xx responses become an `ApiError` and are shown as a toast automatically. Pass `{ silent: true }` when handling the error inline. Raise UI notifications with `alerts.error|success|info|warning(...)`, which works outside React too.
- **Content-Type:** the client only sets `Content-Type: application/json` when there is a body. Fastify rejects an empty JSON body otherwise.
- **Ports are typed** (`text|number|boolean|object|array|messages|any`, default `any`).
  - Compatibility and coercion rules live **only** in `canConnect` in `shared`. The engine validation, the executor's coercion and the editor's `isValidConnection` all use it.
  - Add new types or rules there, together with their table-driven tests.
- **Secrets are write-only:** the API only returns masked hints. The OpenRouter key is the secret named `openrouter`. The master key comes from env `SECRETS_KEY` or `data/.master.key`.
- **LLM providers are records, not code:** a provider record (`providerSchema` in `packages/shared/src/provider.ts`) is a YAML file under `data/providers/`, stored by `ProviderRepository`, a thin subclass of the generic `YamlRepository<T>` that presets also use (`storage/yaml-repository.ts`: a `YamlCodec` supplies parse/serialize/label; the scan, stamping, locks and file naming are shared, so fix them there once).
  - Built-in providers (`builtInProviders`: OpenRouter with id/secret `openrouter`, abliteration.ai with id/secret `abliteration`) live in code, are never stored and are read-only (`409 PROVIDER_READ_ONLY` on PUT/DELETE). Adding one is a new array entry plus the server tests that list built-ins; check the backend's request schema first (abliteration.ai rejects unknown body fields). Stored ids are UUIDs, so a file claiming a built-in id is invalid by schema. Provider route params are `{ id: string }`, not `idParamsSchema`, because of that id. `services/providers.ts` merges built-in and stored records (`builtIn` flag) and strips client bookkeeping (`id`, timestamps, `builtIn`) from bodies.
  - The LLM node resolves its record through `ctx.resources.providers` (snapshotted by `prepareWorkflow`, built-in ids resolved by the engine itself), then picks the `LlmAdapter` for the record's `kind` from the `adapters` map and passes it the record. Unknown id is a node error; a set-but-missing `secret` is the "Missing <secret> secret" error; no `secret` means no key and no `Authorization` header. Never send a record's key to a host other than its `baseUrl`.
  - Tests inject fake LLMs by replacing the `openai-compatible` adapter (`useAdapter`/`restoreAdapter`: `packages/engine/src/test-providers.ts`, `apps/server/src/test-support/adapter.ts`), not by registering provider ids.
  - The single `openai-compatible` adapter (`providers/openai-compatible.ts`) is record-driven: `resolveWireSettings` (`providers/wire-settings.ts`) applies the first matching override per model. An override's `messageName: null` must win over the provider's value, so never resolve it with `??`. `extraBody` is merged last and wins over every computed field. Streamed `raw` always reports reasoning as `message.reasoning`, whatever wire field it came from. Don't add per-backend branches to the adapter; new wire differences become record fields (PLAN.md).
  - **Tools in the adapter** (`docs/plans/tools/`; code in `openai-request.ts`, `openai-stream.ts`, `wire-messages.ts`, `assistant-message.ts`): requests are serialized from the canonical message (`wireMessage`): `tool_calls` and `tool_call_id` verbatim, `content: null` for an assistant message that only calls tools, `provider_data` spread in, `reasoning` under the record's `reasoningReplayField` (null: never), `provenance` and other app-only fields never sent. `tools`/`tool_choice`/`parallel_tool_calls` go out only when set (an empty `tools` list is not sent) and before `extraBody`, which still wins. **Tool calls are kept verbatim**, unknown fields included (`toolCallsOf` only adds a missing `type: 'function'` and `arguments: ''`, and drops the stream's `index`); never re-serialize `arguments`. **Replay fields are record fields** (`replayFields`, `reasoningReplayField`, with per-model overrides like the older ones; a null `reasoningReplayField` override must win, so no `??`), never adapter branches: the named top-level fields of the response message are copied into `message.provider_data` (stream: arrays concatenated, objects merged, anything else replaced). Stream tool-call deltas merge by `index` (`mergeToolCalls`: `id`/`type`/`function.name` set once, `arguments` concatenated, other fields merged); the wire log folds them the same way. `ChatResponse.message` is the canonical assistant message with provenance `{ providerId, model, nodeId }`; the adapter can't know the node, so the caller passes `ChatOptions.nodeId` (required). "No assistant text" is an error only with neither content nor tool calls; a tool call without id or name is an error naming the provider. In the web provider editor the two fields live in the YAML box (`ADVANCED_KEYS`). Tests: `providers/tools.test.ts`; fake adapters in tests build replies with `chatResponse(text)` (engine `test-providers.ts`, server `test-support/adapter.ts`), since `ChatResponse.message` is required.
  - node-ui's provider dropdown takes `{ id, name }` and shows an "Unknown provider (id)" entry when the node's id has no record. User-facing guide: `docs/PROVIDERS.md` (keep it in sync when provider behaviour changes).
  - **Model lists:** `GET /api/providers/:id/models` goes through the adapter's optional `listModels` (`openai-compatible`: `GET <baseUrl>/models`, normalized by `normalizeModels` in `shared`, one generic path, no backend branches). `ModelCatalog` (`services/provider-models.ts`) caches in memory only. Its cache key is the whole record plus `SecretStore.revision`, never `updatedAt`: files edited by hand keep their old timestamp. Any new cache whose data depends on secrets should key on `revision` too. `missingSecretMessage` (engine) is the single source of the missing-secret text. The LLM node's model field stays a plain string; the picker (`ModelPicker`, pure logic in `modelOptions.ts`) only suggests, through `context.loadModels`.
- **Authored collections** (lorebooks, decks; `packages/shared/src/collection.ts`, user guide `docs/COLLECTIONS.md`) are user-written and **read-only for workflows**: Recall and Draw read them through `ctx.resources.collections` (snapshotted by `prepareWorkflow`, the server passes `CollectionRepository`); no node writes them.
  - Storage is `data/collections/<slug>.yaml` through `CollectionRepository`, a thin `YamlRepository` subclass: the same scan, stamping, lock, naming and invalid-file rules as presets and providers. The YAML codec parses every file on read, so `.default()` is safe in the stored schema (unlike JsonRepository records); write bodies use `collectionWriteSchema`, where `entries` is required (a defaulted list on a write would erase them). The serializer leaves out `weight: 1` and `enabled: true`.
  - `parseYamlRecord` (shared by providers, collections and state definitions) stamps a file only when the blank keys are `id`/`createdAt`/`updatedAt`; any other blank value keeps it invalid and untouched.
  - Entry ids are positions (`collectionEntryId(index)` = `entry-<n>`), never stored; nothing may rely on them surviving a save (Draw's `avoidRecent` keys on a fingerprint of the entry text, never the id). An `id` key in a file is just an unknown field.
  - `GET /api/collections` returns summaries (`entryCount`, no entries); editors `GET` the whole record and re-read it on every `collections.changed` (hand edits keep `updatedAt`).
  - `collections.changed` has the presets shape and comes from the directory watcher and from every API write (`services/collections.ts`), always with a fresh `listInvalid()`. `DELETE` answers `409 COLLECTION_IN_USE` (details: workflow names) while a `recall`/`draw` node lists the id.
  - An unknown collection id is a **node error at run time**, not a validation issue (the nodes have static ports). Tags compare trimmed and case-insensitively; a level filter excludes entries without a level; weight 0 is never drawn; Recall keywords are literal with Unicode-aware whole-word edges.
  - Draw's selection is the pure `drawEntries` (`nodes/draw/select.ts`); its `isExcluded` option is how `avoidRecent` leaves out recent draws (`nodes/draw/recent.ts`: `entryKey`, `recentEntryKeys`; see Story state).
  - The web opens a collection through `openCollection` (`pages/collections/collectionActions.tsx`): it fetches the whole record before switching the editor, because the list only has summaries; switching first would show the previous collection meanwhile and push a wrong history entry. The editor's Discard re-reads from disk, and a save answered `404` recreates the collection only after the user agrees in a dialog: a `404` may also mean the file exists but no longer parses (YamlRepository skips invalid files), and a new id would leave Recall/Draw nodes on the old one.
- **Story state** (`packages/shared/src/state/`, README "Story state"): per-chat state that workflow turns write and that lives exactly as long as the replies of the turns that wrote it. Definitions are YAML records (`data/state/definitions/`); the stored truth is `session.state.turns`.
  - **Turn presence is the one rule.** `settleTurn` (`services/settle-turn.ts`) appends a `TurnEntry` for EVERY settled turn (success, failure, stop; writes or not) in the same session update that saves the replies. A turn counts iff `replies > 0` and an assistant message with its `executionId` exists (not `streaming`), or `replies === 0` and `completed`; user messages never count. Counting turns are numbered 1..n and the turn being run is n+1 (`trigger.turn`). Deleting a reply only changes presence; edits (`editedAt`) never touch state.
  - **Stored sessions are not parsed on read** (JsonRepository): read entries only through `readTurnEntries`, append only through `withTurnEntry`, never `session.state.turns` raw.
  - **The fold lives in shared and is the only interpreter** (`foldStoryState`: pure, never throws; the web must reuse it, not re-implement it; pass definitions oldest first with `oldestFirst`). Scalars are **post-values** (`increment` becomes a `set`). A stored value that doesn't fit the CURRENT definition reads as the default plus a warning and stored data is never rewritten, so definition edits are always allowed. Keep `GET /api/sessions/:id/state` small: history keeps values only for number/boolean/enum keys (text and object points are `{ turn }`), the view cuts long write values (`previewWrite` in shared, `WRITE_PREVIEW_LIMIT`, `truncated`) and sends only the newest `NODE_ITEMS_LIMIT` items of an uncapped node collection (`omitted` counts the rest; the fold itself stays uncapped for node keys because Draw's window needs it).
  - **Writes are buffered, reads are the turn-start snapshot.** `ctx.writeState` only buffers (`StateWriteBuffer`, wired into the executor by `StateRun`). A node's requests count only when it completes, and resolve in a fixed order (wave, node id, call order) into `writes` on the result and on `ExecutionFailure.writes`. Templates read only `ctx.state.values`. Item ids are `<executionId>:<nodeId>:<n>`. Implicit node state (`target.kind: 'node'`, Draw's `draws` (`DRAW_STATE_KEY`), keyed by a fingerprint of the entry text, never the positional id) follows the same rules; Draw stores only the first 80 characters of the text next to the key (`memoryText`), since only `entryKey` is ever read.
  - **Read-your-own-writes** (only for the writing node): `ctx.pendingState()` is a `StateAccess` that also shows THIS node's buffered writes; `ctx.state`, templates and other nodes keep the turn-start snapshot. The engine never rebuilds fold inputs: `StateRun.pendingView(nodeId)` resolves that node's requests alone against the run snapshot (`resolveWrites`) and hands them to `executeWorkflow`'s `foldWith(pending)`, cached until the node's next write (without `foldWith`, or without writes, it is the snapshot). The server builds the closure for every run from the exact arguments of that run's snapshot (`foldWithOf` in `story-state.ts`: `startTurn` for a first run, a regenerate's included, and `foldRun` for later runs and the after section), which re-runs the shared fold with `FoldInput.pending`: extra writes folded after everything stored, counted as the running turn's (its number is unchanged: the next turn without `including`, else the included one). A new place that runs a workflow for a turn must pass a `foldWith` built the same way; the preset preview passes none.
  - **Trigger** (`engine/src/nodes/trigger/`, README "Trigger node") gates an injection: score `clamp01((baseChance + growthPerTurn × turnsSinceLastFiring + Σ weight × signal) × (0.5 + volatility))`, one `ctx.random()` roll, and a second draw for the level only when it fires. Its firings are implicit node state under `fires` (one `{ text, level }` item per firing, never anything else, `TRIGGER_STATE_KEY` lives in the node folder, not in shared): cooldowns and `turnsSinceLastFiring` are computed from the folded `itemTurns` (`readFirings`), so deleting a reply undoes a firing; the web shows it through the generic node-write line, no Trigger code outside the node folder, the registry, tests and the panel. Per-level `cooldowns`/`levelWeights` default key by key. Signals are `{ name, weight }` rows that become optional `number` ports (`neverSkips`: a signal from a branch not taken counts as 0 and must not skip the Trigger) through `resolvePorts` (names validated by `signalNameProblem`, shared by the schema and `resolvePorts`); only the custom panel (`panels/trigger.tsx`) edits them. `numberInput` (`nodes/number-input.ts`) is the one rule for a number given to a node input (finite number or numeric text), shared with Draw's `maxLevel`.
  - **Runs on the entry.** A turn's entry records every run in `runs` (`{ executionId, workflowId, part: 'reply'|'post', status: running|completed|error|stopped, error? }`, `error` cut to `POST_ERROR_LIMIT` = 500). `part: 'post'` is a run of the after section (see Reply list). The first reply run creates the entry in `settleTurn`; **every later run settles only through `withRunSettled` (shared)**, which appends its writes AFTER everything earlier (deleting the turn's replies undoes them all). After-section runs are announced `running` in the write that settles the last reply-section run, so the chat never shows a gap. **The restart rule is computed on read**, never stored: `effectiveRuns(entry, isLive)` reports a stored `running` the in-process registry does not hold (`TurnRegistry.hasPostRun(sessionId, executionId)`) as an error ("interrupted by a server restart"); the state view reads again, up to three times, before believing a lost `running` (a run commits its result before the registry lets go of it). The view's per-turn `postStatus`/`postExecutionId`/`postError` are derived from the `post` runs (`postOfEntry`); nothing stores them.
  - **Definition names are immutable under live data:** template-safe, unique ignoring case (`409 STATE_DEFINITION_NAME_TAKEN`), and a rename or delete is refused (`409 STATE_DEFINITION_IN_USE`) while a PRESENT turn wrote it (a delete also while a State node uses it). Updating a definition prunes the workflows' edges to vanished ports; a State node whose key or operation no longer fits is a validation issue naming the node (`WORKFLOW_INVALID`), not a run-time error. `scene` is seeded into an empty directory, and by the Fresh texture example pack (see Example packs).

State Write is a sink whose ops depend on the key type (`stateOpsFor`); every op has an optional `when` input (`requiredIfConnected`, value ignored) so a branch can gate any write. State Write's optional config `value` is a typed JSON literal (`fixedValue`, `nodes/state-write/ports.ts`; `null` = none) used when the `value` input is not connected: the input wins, the literal is validated like an input value, and its presence makes the input `requiredIfConnected` instead of `required` in `resolvePorts` (so ports depend on the config). - **Message links** (`packages/shared/src/links/`, design: `docs/explorations/STATE-DESIGN-AMENDMENT-1.md`): any collection item may link to chat messages; summaries are just items of a collection key whose items link to the messages they cover. There is no summary store, node or session field. The fold does not know about links: linked items live and die with the turn that wrote them like every item.
  - **Shape:** the built-in optional `messages: { ids, fingerprint }` of `collectionItemSchema` (`itemLinkSchema`; `fingerprint` is absent only between a run and the commit check; a bad stored value reads as no link and never loses the item). It is not a declared field: the definitions WRITE schema refuses new fields called `messages` or `link` (`RESERVED_ITEM_FIELDS`), but stored definitions that declare them stay valid: `collectionItem` never copies a value's own `messages` (the built-in link) and nothing else, so an existing declared field called `link` keeps its values (never drop data the user declared); on an item that has `messages` the run's snapshot replaces it with the computed `link`. Ids only, never positions or turn counts: deleting a message shifts every position after it.
  - **Status is computed on read, never stored:** `linkStatus(link, indexById(history))` gives `intact | changed | partial | gone`. `analyzeLinks(items, history)` is the one function behind the planner, Unlinked Messages and the state view (status, surviving ids, 1-based positions, `replaced`, `repeated`). **Replaced:** a non-intact item whose surviving messages intact items of the same key all link (a `gone` item is never replaced). **Chat order:** `chatOrder` (order.ts) is the one rule (by first position, newest first on ties, same-`ids` repeats after the first dropped); `linkedInChatOrder` applies it to a snapshot's items for the `linked` helper and State Read's `linked` read, and `analyzeLinks` marks `repeated` with it for the state view.
  - **A run's snapshot** (`stateSnapshot(story, definitions, history)`) gives collection items with a link a read-only `link: { status, ids, first? }`; nodes and the server use the SAME history (`ctx.history`; the post part keeps the reply part's), so a node's own status and a template's never disagree. A stored item never has a `link`.
  - **Commit-time check** (`commitItemLinks`, pure; the server calls it through `commitLinks` in `services/links.ts`, inside `sessions.silent.update`, from `settleTurn`, `withRunSettled`'s callers and `settleAfterRun`, against `historyMessages` as it is THEN, with the definitions naming the key in the warnings): an `add` whose linked id is not among the history messages, or whose present `fingerprint` no longer matches, is dropped with a plain-language warning; a missing fingerprint is computed and stored. Warnings go to the turn entry's `linkWarnings` (`LINK_WARNING_LIMITS`; later runs append theirs) and the run's execution log (both runners save the log again with them, like the stop warnings). Completed nodes' linked writes of a failed or stopped run still go through the check; the minimal-error settle fallback drops them like other writes. No pairing with `remove` writes. `foldSession(definitions, session, history, scope)` takes the run's history so the snapshot's `link`s are judged with it (`foldRun` builds a later run's); `state-definition-usage.ts` counts Next Chunk and Unlinked Messages as users of a definition.
  - **Nodes are generic, nothing is about summaries.** State Write `add` on a collection key has the `messages` input (`requiredIfConnected`; `messageLink` in `nodes/state-write/link.ts` accepts a link, a message or a non-empty list of messages, anything else is a node error; only `add` reads it, a value's own `messages` stays ignored). **Next Chunk** (History; `definitionId` + `key` of a collection, `chunkSize`, `rawWindow`; `resolvePorts` only checks the target so an unset key is the "not set up" state) plans over the key's snapshot items with `ctx.history` (`planNextChunk`); **Unlinked Messages** (History, static ports, a bad key is a run-time error) drops the messages intact items of the key link. Both locate the key with `locateCollection` (`nodes/state-key.ts`). Memory knows nothing about links; it only has `all` (whole history, `lastN` ignored).
  - **In the state view** (`withLinkViews`, `services/link-view.ts`; contract `itemLinkViewSchema`): the items of a definition's collection key that link to messages carry `link: { status, replaced, repeated, count, missing, firstIndex, lastIndex, firstMessageId, lastMessageId, messageIds }` (1-based positions among history messages, first/last/`messageIds` of the surviving linked messages; absent positions for a `gone` item). Items of node keys get none. The web never recomputes status, replaced or positions: it reads this, and shows markers from `messageIds`.

- **Alternatives** (regenerate and swipes; `packages/shared/src/alternatives.ts`, server `services/regenerate.ts`, `services/alternatives.ts`; design: `docs/plans/frontend-ux/07e-swipes.md`, README "Regenerate and swipes"): an alternative is an ORDINARY TURN (own `executionId`, `TurnEntry`, replies, runs after the reply); alternatives of one turn are tied by the root, the first one's `executionId`, which later ones carry as `alternativeOf`; the replies of every alternative that isn't shown carry `inactive: true` (absent = active, read only as `=== true`, so old messages need nothing). - **Data compatibility (alpha):** user data under `data/` is preserved across upgrades. Schema changes are additive and backward compatible: unknown fields survive via `passthrough`, new optional fields use `.default()`/`.optional()`/`.catch()`, writes migrate-on-write (normalize with `safeParse` + defaults, keep unknown fields, no destructive rewrites). If a breaking change is unavoidable, ship an explicit migration script plus a backup step. Seeds only create missing records and never overwrite user-modified ones. See README Data and secrets.
- **Session writes:** always go through the per-session lock and `update`, never `load → await → save`.
  - The same applies to every mutation of an existing record (characters, personas, avatars): use `update` or the entity lock. Plain `save` is only for creation. Secrets use one store-wide lock.
  - Locks (`storage/lock.ts`) are in-process and **not re-entrant**: never acquire the same key inside its own critical section, or it deadlocks.
  - Messages sent to one session are handled one after another (a regenerate is one of them); different sessions run concurrently. A write that must not overlap a running job (a swipe) checks `TurnRegistry.isRunning` inside its `update` callback, never before it.
  - Repository writes are atomic: they write a temp file, then rename it. The rename retries transient Windows `EPERM`/`EACCES`/`EBUSY` errors.
- **Recency ordering:** the preset, workflow and chat lists are ordered most-recent-first with the shared `compareRecent` comparator (`apps/web/src/pages/recentOrder.ts`: `updatedAt` desc, then `createdAt` desc, then name). Session `updatedAt` means last message activity: only sending a message advances it; message edit/delete and session metadata patches leave it unchanged.
- **Execution semantics:**
  - A workflow has exactly one Chat Input and **at least one sink** (definitions with `sink: true`; Chat Output and State Write so far). Only sinks and the nodes they depend on run; the rest are logged as `skipped` ('not needed by any output'). Replies come only from Chat Outputs; a workflow without one is valid (it runs after the reply when listed below the last replying workflow). Descriptors carry `sink`. Chat Input outputs `message`, `history`, `replies` (what the runs above it saved this turn) and `turn`.
  - Each Chat Output that runs appends one assistant message. Message order is deterministic: dependency first (output Y precedes X when Y's transitive upstream node set is a strict subset of X's, which covers outputs fed by a shared upstream node), then the `order` config only as a priority among outputs with no remaining predecessor, then node id. It never depends on which output finishes first.
  - The speaker name is taken from the connected `character` input if there is one, otherwise from the `name` config, otherwise the message has no name. Messages store a snapshot of `name` plus `characterId`.
  - If no output runs, the turn has no reply and the execution records a warning. On failure, the replies already completed are kept and returned in the error details.
  - `character` is a port data type. The Character node outputs either the session's character or a specific card. A character connected to an LLM node replaces the session character for that node's `{{character.*}}` macros and aliases. The preset input key `character` is reserved.
  - A connected output port that a node doesn't return is an error, unless the port is marked `optional` (Condition branches are).
  - An input marked `required` must be connected, and a skipped source skips the node. `requiredIfConnected` gives the second half without the first: an optional input that, once connected, skips the node when its source was skipped or didn't produce the port (Random chance's `value` and `probability`, so a gate on a branch not taken stays closed). A node can't otherwise tell an unconnected input from a skipped one: both are absent from `ctx.inputs`. A node whose connections are all inactive is skipped, except that inputs marked `neverSkips` never count towards that rule (Recall's extra `text`, its only input, so Recall still scans the messages).
  - On failure, the sibling nodes in the same wave are aborted and settled (status `cancelled`) before the error is thrown. The wait for them is bounded by their original deadline; work that ignores the abort is left running detached and ignored. After that, the execution log must never change.
  - `onEvent` observers can never change the outcome: their exceptions are swallowed.
  - `ctx.log(message)` appends to `nodes[id].logs` (ignored once the node settled, like `recordWire`). Nodes log what a user needs to debug a failure, e.g. Parse JSON's raw input, truncated to 500 characters. Log lines are stored and shown to users like the wire log: never log secrets, headers or unredacted request data, and keep lines short (truncate large inputs).
  - **Randomness:** every run has a seed, `executeWorkflow`'s `seed` option or a `randomUUID()` the engine generates, recorded as `execution.seed`. Nodes draw random numbers only through `ctx.random()` (a deterministic sfc32 stream seeded by cyrb128 of `${seed}:${nodeId}`, `packages/engine/src/seeded-random.ts`), **never `Math.random`**: the same seed and node id give the same sequence, so a run's rolls can be reproduced from its log. The algorithm is pinned by a golden test; changing it breaks reproducing old runs. Each run of a turn has its own seed.
  - **Chat settings in a run:** `executeWorkflow`'s `settings` option holds values already resolved by the caller (`resolveChatSettings`). They reach nodes as `ctx.settings` (frozen, read-only), templates as the `settings` namespace (`{{settings.<key>}}`, `{{settings}}` is compact JSON; `renderPreset` takes them in `templateContext.settings`), and the log as `execution.settings` (`{}` when none). Nodes never read a session's stored values themselves. The Chat Settings node (`chat-settings`) outputs them all (`settings`) and one by `key` (`value`, optional: absent, and logged when the key isn't declared).
  - **Story state in a run:** `executeWorkflow`'s `state` option (a `StateSnapshot`) reaches nodes as the read-only `ctx.state` and templates as `{{state.*}}` and `{{trigger.turn}}`; `ctx.writeState` only buffers, and the result (and `ExecutionFailure`) carries the resolved `writes`. Details under Story state.
  - **Timeouts:** the executor applies a wall-clock deadline per node (`definition.timeoutMs`, default 30s). Nodes whose work is a network call own their real timeout (LLM providers use an idle timeout between stream chunks; http-request uses its `timeoutMs` config) and declare a 10 min `timeoutMs` as a backstop only.
- **Empty sends:** `content` may be empty (or omitted) on `sendMessage`/`streamTurn`. No user message is stored, `userMessage` is absent from the result and failure details, and the turn runs on the session history with `trigger.message` set to `''`. Whether that produces a reply is up to the workflow (empty text slots are dropped). Editing a message to empty stays rejected (`editMessageSchema`).
- **Streaming turns:** the web client sends messages through `POST /api/sessions/:id/messages/stream` (SSE, `turnEventSchema`); the plain `POST .../messages` stays for non-streaming callers.
  - A regenerate of the last turn (`POST .../regenerate/stream`, same `turnEventSchema`, see Alternatives) shares the route plumbing (`streamJob` in `routes/messages.ts`) and the queue slot with messages; a refusal before it starts is a plain JSON error. Stop is `POST .../stop` only: the stream stays open and ends with `turn.error` `TURN_STOPPED`. Failed and stopped turns carry `turnFailureDetailsSchema` in `details` (saved user message, replies so far as `partial` rows, execution), so the client settles from the payload and never guesses with a refetch. Aborting the fetch is a fallback only; it is seen by the server as a `disconnect`.
  - `streamMessage` (`apps/web/src/api/turnStream.ts`) never toasts; `useChat` decides, via `notifyError`.
  - Local row bookkeeping lives in the pure helpers of `pages/chat/turnMessages.ts`. Rows with `status: 'streaming'` are local until the turn settles.
  - **Workflows after the reply hold the turn's queue slot** (`services/turns.ts`, `services/after-section.ts`). The after section is NOT a second `TurnRegistry.run` (it would queue behind a message already waiting): the turn's action adds the announced run ids to `turn.postRunIds` BEFORE the settle write and sets `turn.after` right after `sessions.changed` is published, and the registry resolves the caller's promise first (response or `turn.complete` goes out; the stream is not held open), then runs `after(run)` (`runAfterSection`) with a RunningTurn of its own before releasing the slot. So the next message waits for it, `POST .../stop` stops whichever job is running (a queued message is never the target; the web cancels its own queued message by aborting its request), and a follow-up that throws is only logged. The message routes watch the client from the moment the request arrives (`clientLifetime`), so a queued message whose client leaves is cancelled by `runTurn`'s `signal.aborted` check and stores nothing (`TurnOptions.keepRunning`: the plain endpoint only cancels before the start). Deleting a chat calls `turns.stop(id)` first. The after section never throws: a failure is that run's `error`, a stop by the user ends the running run as `stopped` and records the rest as `stopped` (a `shutdown` stop records the interrupted `error`, like a crash; completed nodes' writes are kept in all of them), a log that cannot be saved is warned and the run still settles, and a deleted session makes the settle a no-op. Each run settles with one `sessions.changed`. `TurnRegistry.close()` (an unconditional `onClose` hook in `app.ts`) stops running jobs with reason `shutdown` and awaits them. Tests that hold an after run use `test-support/post.ts` (`gateNode`, `postHarness`, `waitForPostRun`; `postHarness().setup()` builds a reply and a trailing workflow) and always release it or rely on `app.close()`; `playLater` (engine `test-state.ts`) plays one in memory.
- **Editor:** never drop nodes. Unknown node types are kept as read-only placeholders and are saved unchanged.
- **Presets:** fixed entries that render to empty text are dropped, so a template entry holding only one variable disappears when that variable is empty.
  - **`displayName` vs `name`:** every entry's editor label is the required `displayName`. A message entry's optional `name` is a template rendered like `content`, trimmed, and sent as `PromptMessage.name` only when non-empty. Slots have no `name`. Name templates are validated like content (path `['entries', i, 'name']`); use `entryTemplates`/`entryUsesInput` from `shared` instead of reading `content` alone.
  - **Legacy rule:** an entry with `name` and no `displayName` is a pre-`displayName` entry: its `name` is the label and it has no message name. `upgradeLegacyPreset` (shared) applies this to **raw** data before schema validation, in the YAML loader (`presetCandidate`) and the JSON migration only. Never put it in the zod schema (`z.preprocess` erases the input type the web client relies on) or apply it to API write bodies. Files keep the old shape until their next save.
  - Entry types are `passthrough`, so a stray `name` key compiles anywhere. When building or copying entries, set `displayName`; a leftover `name` silently becomes a message name.
  - **Imported presets** carry a server-owned `source`. Client writes never set it, `PUT` on a preset with one returns 409 `PRESET_READ_ONLY`, and only `services/import/sync.ts` writes it, under `context.importLock`. New connectors implement `ImportConnector` in `services/import/`.
  - The stored `source.hash` covers the connector's `mapperVersion` as well as the file bytes. Any change to a mapper's output for the same input must bump `mapperVersion`, or Sync reports the files as unchanged and never applies it.
  - **Storage is YAML, not JSON:** presets live in `data/presets/<slug-of-name>.yaml` through `PresetRepository` (`storage/preset-repository.ts`). Identity is the `id` inside the file, never the filename. Users may edit or rename files while the server runs, so nothing is cached and every operation scans the directory.
    - Legacy `<id>.json` files are renamed to `.json.migrated` at startup after their YAML is verified. Never delete them.
    - Invalid files are skipped with a warning and never modified. A valid file without `id`/timestamps gets them stamped in place.
    - UUID entry and input ids are not stored: they are re-derived as `entry-<n>`/`input-<n>` on read, and depth-target slots get a readable label id. Never rely on UUID entry ids surviving a save.
    - Mutations go through the id lock and `update`, as with every repository.
  - **Live reload:** a debounced `fs.watch` on the presets directory feeds `GET /api/events` (SSE, `changeEventSchema` in the shared contract). Event `presets.changed` carries the currently invalid files. The watcher is started only from `main.ts` (`createApp(dir, { watch: true })`), never from `createContext`.
    - The web editor never overwrites a dirty draft and keeps the selected entry by position, because entry ids are re-derived on read.
    - New SSE routes that must not block `app.close()` end their streams in the Fastify `preClose` hook, not `onClose`.
- **Change events (`GET /api/events`):** besides `presets.changed`, `providers.changed`, `collections.changed` and `stateDefinitions.changed` (the file-backed resources), the server emits `workflows|characters|personas|sessions.changed` (`{ type, id? }`).
  - They come from `NotifyingRepository` (`services/change-events.ts`), which wraps those repositories in `context.ts` and announces every successful save, update and delete. New write paths are covered automatically. A new record resource gets wrapped there too.
  - `repo.silent` is the raw repository. Chat turns write through it and publish one `sessions.changed` when the turn settles, never per token.
  - Tests that spy on a repository's `get` to pause inside `update` must spy on `.silent`.
  - On connect, every event type is sent once (id-less for records) so clients resync.
  - `providers.changed` has the presets shape (`invalidFiles`). It comes from the `data/providers/` watcher (`watchResourceFiles`, started with the preset one in `app.ts` only when `watch` is on) **and** from `services/providers.ts` after every API write (`publishFileChange`). Always publish with a fresh `listInvalid()`, never `[]`, or an API save clears the warning about a still-broken file. Tests of API-write events use an app without the watcher, which would announce each write twice.
  - Because provider API writes announce **before** the HTTP response, an editor's live sync can see its own save or delete before the response arrives. The provider editor classifies through that (`classifyProviderChange`: a dirty draft the disk already holds is a reload; its own delete is not "removed from disk"). Never assume the response comes first.
- **Chat settings** (`packages/shared/src/chat-settings.ts`) are user-owned per-chat knobs that the workflow declares (`workflow.settings`) and the session stores (`session.settings`).
  - Both fields are `.optional()`, not defaulted: stored records are never parsed on read. Read declarations with `workflowSettings()` (which also tolerates a non-list) and values with `session.settings ?? {}`; never trust the zod output type for a raw record.
  - Readers that need one declaration per key go through `usableSettings` (usable key, first declaration wins): the resolver, PATCH validation, hints and the chat panel must agree on duplicates.
  - The workflow editor keeps the stored list raw (`withDraftSettings`): a declaration that doesn't parse (`parseWorkflowSetting`) is a read-only row the user can only remove, never dropped on load (that would delete it on the next save). Save and Duplicate refuse such a draft with a plain message (`unsavableSettings`) instead of the API's 400.
  - Turns never write them and message edits/deletes/regeneration never rewind them. Only `PATCH /api/sessions/:id` changes them: a partial merge where `null` removes a key (any key); a non-null value for an undeclared key or a value that doesn't fit is `400 CHAT_SETTING_INVALID` and writes nothing (`mergeSettings` in `services/sessions.ts`). Like every metadata patch it never advances `updatedAt`.
  - `resolveChatSettings` is the single resolver (server turns, preset preview, the chat panel): a stored value is used when it fits, else the default with an issue; stored data is never rewritten; undeclared stored keys are kept and ignored. Keys must pass `isSettingKey`: an identifier, and not reserved (`__proto__`/`constructor`/`prototype`, the Handlebars literals `this`/`true`/`false`/`null`/`undefined`, and `toString`, which the template data defines on `settings`). The preset preview without a session uses each key's default (`settingsCatalog`).
  - `startTurn` snapshots the resolved values; the run records them in `execution.settings` and the resolver's issues in `execution.warnings`. Declaration problems are `prepareWorkflow` issues (`workflowSettingIssues`).
- **Creating a session** takes a `workflowId` (legacy shape: no `triggers` stored) or a `triggers` list, exactly one. Sessions also store `characterId` and `personaId`, which the server loads and passes to the executor.
- **Reply list (triggers)** (`packages/shared/src/triggers.ts`, plan `docs/plans/triggers/`, design `docs/explorations/TRIGGERS-PROPOSAL-1.md`): a chat runs an ordered, toggleable list of workflows on each reply, `session.triggers.reply: { workflowId, enabled }[]`.
  - **`replyWorkflows(session)` is the only reader** (a legacy chat reads as its `workflowId` alone). `session.workflowId` mirrors the list's first entry for older readers; never read it to decide what runs or which settings exist. The settings union of a list is `listedSettings` (PATCH validation, preset preview, the chat panel); a run resolves against its own workflow only.
  - **One firing is one turn**: one `TurnEntry` whose `executionId` (the turn id) is the first run's log id; every message of the turn carries it, and each reply also carries `runId` (its own run's log: open logs with `runId ?? executionId`). The entry's `runs` records every run (`part: 'reply'|'post'`, status, error). Later runs settle into the entry only through `withRunSettled`; new entries never write `postExecutionId`/`postStatus`/`postError` (read them through `postOfEntry`/`effectiveRuns`, which also cover legacy entries).
  - **Run k sees what runs 1..k-1 did** (`services/reply-section.ts`, `after-section.ts`; `foldRun` is the one way a later run folds its start state): their committed writes (`foldSession`'s `including: turnId`, so the turn counts while it runs) and the chat as it stands (from the first reply on, the turn's user message, then the replies). Every fold made for a run passes its `workflowId`.
  - **Node-private state is scoped by workflow**: node targets carry `workflowId`; a node reads its own workflow's writes plus legacy ones without `workflowId`.
  - **Two sections** (split in `startTurn`): the reply section runs from the top down to the last workflow with a Chat Output node (streamed; it ends with `turn.complete`/`turn.error`), the after section runs the workflows below it in the queue slot after the result is sent (see Streaming turns). An empty reply section completes the turn at once with no reply (`execution` is then absent from the result). A failed run keeps what it completed and the next runs still run, in both sections; a stop ends the list. `RunningTurn.postRunIds` is a set.
  - **Web** (`pages/chat/panel/`: `ReplySection`, `useReplyList`, pure `replyList.ts`, `replySaver.ts`): the chat panel's "On reply" section is the only editor of the list (the header has no workflow select). It saves through `createReplySaver`/`useChat.updateReplyList` (one PATCH in flight, never gated by a running turn, only `triggers`/`workflowId` taken from the answer; header metadata patches keep the local list, `withStoredMetadata`). `Chat.tsx` memoizes `replyWorkflows` on `session.triggers` and `workflowId` so tokens don't re-render the panel. A new chat copies the open chat's list. Streaming rows are keyed by `runId` + node id; a row still streaming has a `runId` but no saved log, so never render `ExecutionDetails` for it. Open a message's log with `messageLogId(message)` (`runId ?? executionId`). `NodeMemory` keys and every reader of a node-write target compare `workflowId` too. When a turn has `runs`, read them, not the derived post fields.
- **Characters/personas:**
  - Card parsing and writing (PNG `tEXt` chunks `ccv3`, which takes precedence, then `chara`; V1/V2/V3 JSON) lives in `apps/server/src/card.ts` and runs on the server.
  - Export writes both `chara` (V2) and `ccv3` (V3), like SillyTavern.
  - Unknown card fields are kept in `extensions` so export round-trips.
- **Templates are Handlebars:** preset content and template-taking node configs are rendered with the `handlebars` runtime (`noEscape: true`) over a data object built from the turn context. Blocks (`{{#if}}`, `{{#each}}`), `{{else}}`, subexpression comparisons (`{{#if (eq character.name "x")}}`), and `{{! comments}}` are supported; the exact syntax and helper list are documented in the README.
  - The macro registry in `packages/shared/src/macros.ts` still defines every available path, and the helper list lives next to it. Preset validation walks the parsed AST, so editor hints and warnings stay in sync with what renders. Never hand-write hint lists.
  - Macro names are namespaced by source: `{{character.<field>}}`, `{{persona.name|description}}`, `{{input.<key>}}`, `{{trigger.*}}` (including `trigger.turn`), `{{settings.<key>}}` (keys come from workflow declarations: `macroHints(inputs, settings)` hints them, `settingsCatalog` unions them across workflows; never hand-write a key list) and `{{state.<definition>.<key>}}` (`macroHints`' third argument, built by `stateHints(definitions)` from `stateDefinitionsStore` in both the preset editor and the node panels' template fields via `NodePanelContext.stateDefinitions`; unknown paths render empty without a warning).
  - Short aliases: `{{char}}`, `{{user}}` (defaults to "User"), `{{description}}`, `{{personality}}`, `{{scenario}}`, and `{{persona}}` (the persona description).
  - `{{char.*}}`/`{{user.*}}` were removed on purpose. Don't add legacy `<BOT>`/`<USER>` or SillyTavern's extra macros unless asked.
  - Templates are **case-sensitive** (stock Handlebars resolution).
  - Unknown macros render as **empty text** (stock Handlebars). Unknown paths in enabled entries still produce a preset warning.
  - A known macro with no value renders as empty text.
  - Macros also resolve inside character and persona fields, with protection against cycles.
  - Unknown `{{input.x}}` is a preset validation **error**.
- **Prompt behaviour is chosen by the user:** the engine never applies automatic SillyTavern rules (card system prompt overriding the main prompt, splitting examples at `<START>`, and so on). Users reference fields in their presets themselves.
- **Prompt messages** have an optional `name`, passed through to the provider only when set. Preset message entries set it from their `name` template; messages slots carry the history's names. A future "speaker names" option on the history slot builds on this.
- **Prompt messages are the OpenAI Chat Completions message** (`packages/shared/src/conversation/`, plan `docs/plans/tools/`): `promptMessageSchema` is `conversationMessageSchema` (passthrough): `role` `system|user|assistant|tool`, `content` (**always a string**; a tool-calling assistant message has `''`, the adapter sends `null`), `name`, `tool_calls` (assistant only; each call and its `function` are passthrough, `arguments` is the raw JSON text, never re-serialized), `tool_call_id` (required on `tool`), plus the app-only `reasoning`, `provider_data` and `provenance { providerId, model, nodeId }`, which the adapter never sends as is. Tool field names stay snake_case. `messageBlocks` is the unit a prompt never splits; `repairToolSequence` (orphan tool messages and unanswered calls removed) runs on the final prompt only, never on stored data. Tool names follow `toolNameSchema`. `messages-to-text` writes calls as `assistant -> name(arguments)` and results as `tool <name>: <content>`.
- **LLM node option** `mergeSystemMessages`: merges consecutive system messages that have no name, after rendering.
- **Wire log:** an LLM node logs what actually went over the wire in `nodes[id].wires`, **a list with one entry per HTTP call** (`wireExchangeSchema`: `url`, `method`, redacted `headers`, the exact `body` object given to `fetch`, `status`, `response`; a stream's chunks are folded under the backend's own field names). The single `nodes[id].wire` of older logs stays parseable and is shown by the web, but is no longer written.
  - Adapters report it through `ChatOptions.onWire` (the node passes `ctx.recordWire`): once before `fetch`, again with the response. Each report replaces the last, so a failed call keeps what was sent. `ctx.recordWire` updates the node's current entry; **a node that makes several calls calls `ctx.beginWire()` before each one**, which makes the next report append a new entry (the LLM node does, once per call). The web's execution details number the calls when there is more than one (`WireList`).
  - Redaction happens **inside the adapter**, before the callback (`providers/wire-log.ts`): credential-looking header names are masked and the secret value is scrubbed everywhere, including the adapter's thrown error messages (they reach `nodes[id].error` and toasts). Never hand an unredacted exchange out of the adapter.
  - The canonical `request` field exists only in older logs. Keep it parseable and displayed as a fallback.
  - Non-stream reasoning: after `chat`, the LLM node emits `ChatResponse.reasoning` as one `reasoningDelta`, so it reaches the chat like streamed reasoning. Never emit it on the stream path, or it doubles.

## Adding a node type
1. Create `packages/engine/src/nodes/<type>/index.ts` exporting a `NodeDefinition`: `type`, `label`, `category`, typed `inputs`/`outputs` with `dataType` and `description`, zod `configSchema`, `defaultConfig`, and `execute(ctx)`, which returns one key per output port.
   - Set `sink: true` only for nodes that must run even when no Chat Output depends on them (they write somewhere).
2. Register it in `registry.ts`.
3. Add tests in `nodes.test.ts`.
4. The UI picks it up automatically through `/api/node-types`. Add a custom panel in `node-ui` only if the generated form isn't enough.
   - If the definition has `resolvePorts`, its descriptor gets `dynamicPorts: true`, and the editor resolves inputs and outputs for it. Never add per-type branches in the web app.
   - After handles change, refresh React Flow's node internals.
   - A port resolution that fails toasts once per node (`createPortErrors`, `pages/workflows/dynamicPorts.ts`); the toast goes away when the node resolves or is deleted. A node that is not set up yet (a required text setting is still blank, `unsetSettings` reads it off the config schema's `minLength`) toasts nothing: its panel says what to pick.
   - Edges to ports that disappear are **pruned** (the connection is dropped) once the node's ports resolve without them. Pruning only happens when the ports resolved successfully: unknown types and failing resolvers keep their edges.
   - The same prune rule lives in the engine (`pruneInvalidEdges`) and runs on preset update and workflow save; the editor applies it when a dynamic node's ports re-resolve. Prune the handle, never the node.

## Gotchas
- **Alpha stage, user data is preserved:** never reset or delete `data/`; schema changes must be additive + backward compatible (see Key contracts). Corrupt JSON files are never auto-deleted (`list()` skips with a warning, `get()` throws with the file path).
- **Never run tests or scripts against `apps/server/data`.** Tests use temp dirs. For live checks, run the server from a temp cwd or against a copy of the data.
- **Seeds must be idempotent and non-destructive:** they only create what's missing, so restarts never duplicate anything and never overwrite user-modified records.
- **React Flow editor:** keep nodes and edges as **controlled state**. Don't rebuild them from workflow data on every render; that breaks dragging and selection. This was a past bug.
  - **Copy/paste of nodes** uses the native `copy` and `paste` events, never `navigator.clipboard` (no permission, works across tabs). They are `copy`/`paste` handlers of `useShortcutArea` (`keyboard/shortcutAreas.ts`, `runClipboard`), dispatched by `useKeyboard`'s `document` listeners under the same rules as the key shortcuts (the view with the keyboard, not in a field or a dialog); a handler returns true only when it acted, and only then is `preventDefault()` called, so a copy with nothing selected and a paste of ordinary text go on normally. The payload (`kind: 'serious-tavern/nodes'`, `version: 1`) and the paste rules are the pure `canvasClipboard.ts`; a paste is ONE `recordStep` (`useCanvasClipboard`). Node names always come from `withDisplayNames` (`model.ts`), shared by `addNode` and paste.
  - **Canvas history** (`pages/workflows/canvasHistory.ts` pure, `useCanvasHistory.ts` wiring): snapshots hold nodes and edges without selection, `dragging`, `resizing` or `measured` (`snapshotOf`), and a restore keeps the live nodes' `measured` (`restoreNodes`) so they don't blink out. The canvas calls `history.record(before?, groupKey?)` right BEFORE it changes nodes or edges; calls in the same tick count once (one user action may change nodes and edges), a `groupKey` repeated within a second joins the last step (`config:<nodeId>`), and a drag records its start snapshot on drag stop only if a node moved. Anything new that edits the draft (paste) calls `recordStep()` (returned by `useWorkflowCanvas`) once before applying. `load`/`clear` reset the history (so Revert does); saving doesn't. Edges pruned by `useDynamicPorts` are not recorded: it uses the raw setters, never `record`. Undo/redo set nodes and edges directly, never through `onNodesChange`/`onEdgesChange` (that would record).
- **Environment:** Windows/PowerShell.
  - Stop processes only by PID. Find them with `Get-NetTCPConnection -LocalPort 3001,5173 -State Listen`.
  - Killing the npm/npx parent leaves node child processes running.
  - `&&` only chains native commands.
- **Git worktrees:** `@st/*` resolves through `node_modules/@st` links. Without the worktree's own links, the packages resolve to the main checkout, so tests and typecheck silently use the wrong `shared`. Create junctions for `shared`, `engine` and `node-ui` inside the worktree's `node_modules/@st`.
- **Windows 8.3 short paths:** `fs.watch` on a directory given by its short name (e.g. `C:\Users\JEANHA~1\...`, what `os.tmpdir()` returns here) kills the whole process with a libuv assertion. Watch `fs.promises.realpath(dir)`.
- **Nested worktrees break Biome:** a leftover worktree under `.claude/worktrees/` (it contains its own `biome.json`) makes `biome check .` fail on the main checkout with "nested root configuration". Remove finished worktrees: unlink their `node_modules/@st` junctions first (`[System.IO.Directory]::Delete(path, $false)`), then `git worktree remove`.
- **Tooling:** pnpm isn't installed; use npm. The user's Windows machine has no browser automation set up, so UI changes there need a manual check by the user. Cloud containers have Chromium and Playwright at `/opt/pw-browsers` (never run `playwright install`); the state phases' live checks ran there.
- **Case-only file name clashes:** on Windows, sibling files differing only by case (`ModelPicker.tsx` and `modelPicker.ts`) fail typecheck with TS1261. Pick distinct names.
- **Contract coverage:** `app.test.ts` requires every contract endpoint to be exercised, so a new contract entry, its route and its test land in the same commit.
- **Comboboxes and Biome a11y:** options are `div role="option" tabIndex={-1}` inside a `div role="listbox"` (an `li` fails `noNoninteractiveElementToInteractiveRole`). Each option needs `onMouseDown={e => e.preventDefault()}`, or the input's blur closes the list before the click lands.
- **SSR panel tests** (`renderToStaticMarkup`) don't run effects: a hook's initial state must already be right without them.
- **Live server checks on a data copy:** run `node <repo>/node_modules/tsx/dist/cli.mjs <repo>/apps/server/src/main.ts` with the copy's parent as cwd (the server uses `./data`) and `PORT` set (the startup log always says 3001). `node --import tsx` fails from a temp cwd because tsx doesn't resolve there. Delete the copy afterwards: it holds the encrypted secrets and the master key.
- **Line endings:** `.gitattributes` pins text files to LF (`* text=auto eol=lf`). Write new files with LF; don't mass-reformat unrelated files.
- **Server integration tests that build a workflow by hand** must include exactly one `chat-input` node, even when its outputs are not wired to anything. `prepareWorkflow` rejects workflows with zero or multiple chat-input nodes before execution begins.
- **Verification:** for server changes, a quick live check is to start the server with `npx tsx src/index.ts` in `apps/server` and `curl.exe` the endpoints.

## CodeGraph

In repositories indexed by CodeGraph (a `.codegraph/` directory exists at the repo root), reach for it BEFORE grep/find or reading files when you need to understand or locate code:

- **MCP tool** (when available): `codegraph_explore` answers most code questions in one call — the relevant symbols' verbatim source plus the call paths between them, including dynamic-dispatch hops grep can't follow. Name a file or symbol in the query to read its current line-numbered source. If it's listed but deferred, load it by name via tool search.
- **Shell** (always works): `codegraph explore "<symbol names or question>"` prints the same output.

If there is no `.codegraph/` directory, skip CodeGraph entirely — indexing is the user's decision.
