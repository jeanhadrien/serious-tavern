MESSAGE LINKS AND SUMMARIES AS STORY STATE (STATE-DESIGN-AMENDMENT-1).

SHARED
- Collection items gain the optional built-in `messages: { ids: string[], fingerprint: string }` (not a declared field; every collection accepts it). Stored in the `add` write; the fold is unchanged (it already carries items through). A `value` object's own `messages` key stays an ignored undeclared field: links only come from State Write's `messages` input.
- `linkStatus(item, history)` (pure): `intact | changed | partial | gone`, per the amendment's table; table-tested. One function used by the state view, the turn snapshot and the web model.
- "Replaced" (pure): a non-intact item is replaced when intact items of the same key link every one of its surviving messages. "Linked in chat order" (pure): the intact linked items of a key, sorted by their first linked message's position, duplicates (same messages) after the first dropped. Both table-tested; used by Next Chunk, the `linked` helper, State Read, the view and the panel.
- Commit-time link check (generalize `commitSummaryWrites`): for every `add` write whose item has `messages`, against the history messages at commit time: unknown id → drop the write with a warning; `fingerprint` present and not matching → drop with a warning; `fingerprint` absent → compute and store it. No pairing with `remove` writes (a separate State Write node writes those). Warnings go to the turn entry's `linkWarnings` (capped like `summaryWarnings` was; `.optional().catch(undefined)`) and the run's execution log.
- Template helper `linked` (`{{#each (linked state.memory.summaries)}}`): listed with the helpers in shared so hints and preset validation know it; returns the linked-in-chat-order items of a collection value (anything else → empty list). Document it in docs/TEMPLATING.md and the README helper list.
- `planNextChunk(history, items, chunkSize, rawWindow)` reads items with links (items without `messages` are ignored); "covered" means linked by an intact item; the first non-intact, non-replaced item with surviving messages outside the raw window is re-planned (its id as `replaces`). Remove `composeHistory`.

ENGINE
- Turn-start snapshot: collection items carry a read-only computed `link: { status, ids }` when they have `messages` (from `linkStatus` over the run's history). Templates and State Read see it. Never stored.
- **State Write:** for `add` on a collection key, an optional `messages` input (`requiredIfConnected`; resolved by `resolvePorts`, absent for other ops/types). Accepts a link `{ ids, fingerprint? }` (Next Chunk's `link`), a message, or a list of messages (ids taken in order; e.g. After Reply's `replies`); anything else is a node error naming what it got. The buffered `add` carries the link; the commit check above applies.
- **Next Chunk:** config `definitionId` + `key` (a collection key; same picker rules and port resolution style as State Read, an unset/unknown target is a node-not-set-up state like State Read's), `chunkSize`, `rawWindow`; optional `after` input; outputs `messages`, `text`, `link` (`{ ids, fingerprint }`) and `replaces` (text, the broken item's id), all optional. Plans over that key's folded items.
- **Unlinked Messages** (`unlinked-messages`, category 'History', not a sink): input `messages` (messages, required); config the same collection-key picker; outputs `messages` (the input minus messages linked by intact items of the key, in input order) and `text` (Memory's transcript format). An unknown or non-collection key is a node error at run time, like Recall's unknown collection.
- **State Read:** a read mode for collection keys giving the linked-in-chat-order items (decide the mode name in the plan; reuse `stateReads` in shared so the panel lists it).
- **Memory:** restored to its pre-phase-6 code and tests (remove `summarySet`; check nothing else changed). Decide in the plan whether to add an explicit "all messages" setting (amendment open question 1; additive, `lastN: 0` keeps meaning none).
- **Save Summary:** deleted (node, registry, tests, docs). Workflows saved on this branch that still hold a `save-summary` node load as unknown-type placeholders (the editor's existing rule); fine, no migration.
- Tests: link status on the snapshot; State Write with each accepted `messages` shape and the rejected ones; Next Chunk over a state key (fresh chat, partial chunk, raw window, broken middle item re-planned, replaced item skipped, all gone); Unlinked Messages (intact hides, broken doesn't, order kept); `linked` helper and State Read mode order; the summary chain's writes undone with the turn (fold); the post-part repeated-node rule still drops repeated nodes' writes.

- `GET /api/sessions/:id/state` (contract first): collection items that have a link carry `link: { status, replaced, count, missing, firstIndex, lastIndex, firstMessageId, lastMessageId }` (1-based indexes among history messages; first/last of the surviving linked messages). Remove `summaries`. Decide in the plan whether linked items' text is sent whole or cut (`previewWrite`) with a way to read the full text on expand (amendment open question 2).
